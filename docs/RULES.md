# FM WORKS 運用・開発ルール

対象：v0.0.0（Sites開発初版） / 更新：2026-10-18

## 1. 位置づけ

現在の開発アプリを扱うルールを定める。会社の就業規則・旅費規程・承認規程を新たに制定するものではない。アプリ内の見本文書・金額・勤務設定も架空である。正式運用の会社規程と現在のプログラムの動作を混同しない。

ユーザーの最新指示を優先する。機能は要件定義書、構成は技術設計書、この文書は運用・変更手順の正本。同じ内容の役職別資料・引継ぎ書・計画書・進捗ファイルを増やさない。過去の差分はGit履歴・PRで確認する。

## 2. データとアクセス

- 入力・取込みはすべて架空データ。実社員・顧客・取引・口座・給与・実務資料を入れない。
- 保存先はSites内蔵SQL/D1。ブラウザーは表示用状態と設定・トークンだけを保持する。スプレッドシート・GASへ接続しない。
- 明示指示まで現在の所有者限定を維持する。アプリ内の担当者選択を本人認証と扱わない。
- 更新公開でDBを消したりseedを入れ直したりしない。データ修正は対象・条件・結果を特定し、一括初期化で代用しない。
- アクセストークン・cookie・認証用URL・秘密鍵をGit・添付ファイル・ログに保存しない。

## 3. 現行の業務制御

以下は現行コードを読むための要約。新しい会社規程や外部法令の解釈ではない。

| 領域 | 現行の条件 | 参照 |
|---|---|---|
| 権限 | サーバーで判定する。画面の非表示だけに依存しない。リーダーは直属部下を扱い、自己承認は不可 | `Code.js`, `Requests.js`, `Monthly.js` |
| 社員 | 上司関係の循環、最後の有効管理者を失う変更を防ぐ | `Employees.js` |
| 勤怠・工数 | 状態・日付・時間・案件を検証し、締め済み期間の通常変更を拒否する | `Code.js`, `Worklog.js`, `Monthly.js` |
| 有給 | 台帳・残数を対応させ、残不足・重複消化・取消時の重複返還を防ぐ | `LeaveLedger.js`, `Requests.js` |
| 有給の自動管理 | 入社日と明示設定を使う。標準付与列は10/11/12/14/16/18/20日。出勤率・履歴を確認できないものを無条件に付与しない。日次ジョブは未対応 | `AnnualLeaveAutomation.js` |
| 労務設定 | 未確定を確定扱いしない。週開始日・対象期間・休日等の設定を要する。正式な就業規則・協定の代わりにしない | `Labor.js`, `Monthly.js` |
| 見積 | 本人・管理者の範囲、入力・金額・明細・改訂・依頼キーを確認。正式発行は未対応 | `Quotes.js` |
| 経理・総務 | 管理操作は管理者または認められた経理・総務部署に限定。金額や申請状態を検証 | `Finance.js`, `Somu.js`, `SomuGrowth.js` |
| 資金繰り | 管理者限定。明細・予定・振替・照合・改訂を確認。同じ依頼キーの別内容を成功扱いにしない | `CashFlow*.js` |
| 文書・案件 | 対象・権限・改訂を確認。未対応の添付・発行を保存成功として表示しない | `CompanyDocs.js`, `Project*.js`, `Documents.js` |

参照ファイルはすべて`src/domain/`内。日付と業務時刻はAsia/Tokyo基準。検証範囲と未受入機能は[要件定義書](REQUIREMENTS.md)を参照する。

## 4. 配置と削除

画面は`src/ui/modules/`、CSSは`src/ui/styles/`、共通描画は`src/ui/components/`、業務は`src/domain/`配下の業務分野別フォルダー、ブラウザー連携は`src/browser/`、HTTP/SQLは`src/server/`へ置く。入口・DB・ビルド・テスト・文書を対応する場所へ置き、個人名・役職名・過去の作業名でディレクトリを増やさない。

削除前にimport、HTML組込み、生成、ビルド・マイグレーションからの参照を確認する。未使用と確認できるサンプル・画像・部品・重複文書・古い公開手順を削除する。互換名が古いという理由だけで使用中の関数を消さない。

生成物は直接編集しない。`src/generated/`と`db/seeds/workspace.json`は再生成する。適用済み`drizzle/`のSQL・タグ・履歴は変更・削除しない。スキーマ変更は追加マイグレーションとし、データ修正は別に扱う。第三者ライセンスは対象コードと一緒に維持する。

## 5. 変更・検証・統合

1. 最新main・関連PR・文書・Sitesソースを確認する。専用ブランチを使い並行変更を保持する。
2. 目的、影響する画面/API/DB、完了条件を決める。コードと該当正本文書を同時に変更する。
3. 生成、回帰テスト（未認証APIの早期拒否・日付時刻変換を含む）、型チェック、ビルドを行う。依存変更時はmanifest・lockfile・インストールを合わせる。
4. PRへ理由・削除対象・検証結果・未確認範囲を書く。base/headを確認して統合する。競合は最新変更を読んで解決し強制上書きしない。
5. 同じSiteへソース同期・保存・公開し、GitHub mainの内容と照合する。

GitHub Actions・Codespaces・有料ランナーは使わず、GPT環境で検証する。依頼済み修正・統合・試作公開で同じ許可確認を繰り返さない。

## 6. 完了判定

テスト、ビルド、GitHub統合、Sites公開、公開後操作はそれぞれ確認する。重要な変更は公開先の読取と保存後の再取得を確認する。ブラウザーQAができなければ未実施と明記し、画面操作確認済みとは書かない。

未対応・未検証を「問題ゼロ」「正式運用可能」と断定しない。回数を満たすための無意味な変更は加えず、具体的な問題・修正・再検証の根拠を残す。

## 初版の削除基準

旧GASの実行入口・トリガー・バックアップ・Sheetsスキーマ変更だけを除去する。Sites側で現在使う業務関数や、D1の既存データ・適用済み変更履歴・監査証跡は削除しない。実データ初期化、Git履歴改変、無断公開範囲変更は禁止する。
