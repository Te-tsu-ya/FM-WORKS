# FM WORKS｜経理機能の受入検証手順

更新：2026-10-10  
対象：経費精算申請・出張報告・経費記録・承認／差戻し／精算・証憑照合・監査ログ・読込速度

## 検証環境・ルール

- **本番FM WORKS DBへの架空データ登録は禁止。** 実登録・実削除を確認する場合は、異なるスプレッドシートIDとGASの検証専用デプロイを用意する。
- 検証環境は実在する顧客・社員情報を使わない。架空の申請者（社員権限）、架空の経理担当（経理権限）、架空の管理者（ADMIN）の3種類を用意する。
- 監査ログが失敗した場合、**本体登録済みと監査未確認は別の状態**。同じ内容を新しいキーで再送せず、まず履歴のIDを検索する。
- 承認・精算の動作は資金移動を伴わない。ただし「精算済」の状態変更は正式な会計処理と誤認されないよう、検証用のみに限定する。
- 本番ログイン権限なしに「本番実登録済み」「0秒ロード」と報告しない。

## A. 本番の読み取り専用チェック

1. 通常権限でログインし、申請・報告メニューから経費・出張の登録フォームが開けることを確認。保存ボタンを押さない。
2. 経理権限のないユーザーが経理一覧を閲覧できないことを確認。
3. 経理権限でログインし、経理一覧・サンプル表示・実データへの切替ができることを確認。サンプル表示中は書込APIが送信されない。
4. 初回・再訪の読込秒数を10回ずつ記録し、中央値（p50）と95パーセンタイル（p95）を出す。端末、回線、件数、実行日時、GAS版を同時に記録する。
5. 表示中の検索・対象月変更・行選択で新しいGAS通信が発生しないことを確認する。
6. ブラウザのPC・スマートフォン相当の幅（1366px/390px/320px）で主要ボタンが操作できることを確認する。

## B. 専用検証DBでのみ行う書込試験

| ID | 操作 | 合格条件 |
| --- | --- | --- |
| F-01 | 社員が架空経費2,500円を新規申請 | ID発行、経費精算申請に1行のみ保存、本人の履歴で承認待ち |
| F-02 | 同じ送信識別子で同じ申請を再送 | 新しい行なし、duplicate=true、元のIDと監査記録の存在を返す |
| F-03 | 同じ送信識別子で異なる金額を再送 | エラーで拒否、元の金額のまま |
| F-04 | 経理権限で承認 | ステータス承認済、承認者・時刻・監査ログの一致 |
| F-05 | 本人による承認・精算を試行 | サーバー側で拒否 |
| F-06 | 経理権限で精算を確認 | 精算済の状態・日付・監査ログ一致、銀行振込は発生しない |
| F-07 | 出張を申請→差戻し→修正再申請 | 同じIDで内容更新、改訂分の監査ログが照合できる |
| F-08 | 経費記録の証憑整理番号と申請の番号を照合 | 1:1で金額一致なら一致。複数申請なら要確認 |
| F-09 | 保存途中で通信を切り、同じキーで再送 | 行を重複作成せず、監査ログの有無も再確認 |
| F-10 | 監査ログの書込失敗を模擬 | 本体は保存済み、auditRecorded=false、二重登録しない警告を表示 |
| F-11 | 経理書込中にEsc・背景クリック・連打 | 書込中は画面を閉じず、同じ内容を多重送信しない |
| F-12 | ログアウト直後に遅いサーバー応答を返す | 以前の利用者の経理情報を画面へ表示しない |

## C. 性能の目標値と限界

- 検索・絞込・行選択は**サーバー通信0件**（ローカルで即時更新）を必須とする。
- 初回取得はApps Scriptの起動・認証・スプレッドシート取得・ネットワークに左右される。0秒を保証しない。計測値がない限り「高速化達成」と断言しない。
- ボトルネック切り分けは、画面に表示する「前回API応答」と「サーバー内処理」の差で行う。
- 改修前後の同条件でp50・p95を比較し、p95の悪化やタイムアウトの増加があればリリースを差し戻す。

## D. 受入判断と運用

- まずGitHub Actionsの経理・書類・総務・勤怠回帰テストを全件通過させる。
- 専用検証環境のF-01〜F-12と本番読み取り専用チェックが通過した場合のみ、経理の実業務受入を「完了」と評価する。
- どれかが未実施であれば「コード検査済み／実業務受入未完了」と報告する。
- 監査ログ欠落を発見した場合は、履歴ID・操作時刻・操作主体を調べ、権限者が原因を確認する。自動で二重の監査行を作って解決した扱いにしない。
