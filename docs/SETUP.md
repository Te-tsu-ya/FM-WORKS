# FM WORKS 初期・本番セットアップ

> **GitHub Actions枠を消費せず、通常のChatGPTからGAS公開を予約する方法:** [`GAS_NO_ACTIONS_BRIDGE.md`](GAS_NO_ACTIONS_BRIDGE.md) に、所有者PCで動作するローカル公開ブリッジの初回設定・検証・公開・公開確認方法を記載。初回Google認証／PC常駐登録が完了するまでは「自動公開できる」と報告しない。

## 1. GPT検証と直接公開（2026-10-12以降）

最初に[AGENTS.md](../AGENTS.md)を読む。GitHub Actionsは自動／手動とも禁止。無料枠の復活時も利用しない。旧ワークフローは `.github/workflows-disabled/` に保管するだけで、復元しない。

1. 最新mainを取得し、専用ブランチで改修する。
2. GPT環境で `node scripts/run_local_checks.mjs` を実行する。ブラウザーが使えない場合は `--functional` とし、画面確認は未実行と明記する。
3. 対象ソースと検証記録をPRに残し、mainが進んでいないか確認して統合する。ActionsのCIを待たず、ローカル結果を判定する。
4. 公開する場合は、所有者が認証済みのApps Script操作またはローカルclaspを使用する。GitHub Secretsから認証情報を取り出すためのActionsは作成しない。
5. ローカルclaspは既存スクリプトに接続し、`node scripts/generate_docs.mjs` 後に `clasp push --force`、既存デプロイIDを指定した `clasp create-deployment --deploymentId <既存ID>` で更新する。接続先・既存IDを変更前に確認する。認証情報をリポジトリへ保存しない。
6. 同じ公開IDの版番号更新を確認する。ソースpushのみを公開成功と扱わない。DB更新と認証付き実操作も別に記録する。

以下の過去のActions説明は履歴であり、この運用方針より優先しない。

## 2. 初期ADMINのPIN設定

認証情報が1件もない場合、FM WORKSは通常ログイン画面ではなく「初期管理者設定」を表示します。

1. Webアプリを所有者のみアクセス可能な状態で開く
2. ADMIN権限の社員IDを入力
3. 本人だけが知る6桁PINを設定
4. PINをチャット・GitHub・ドキュメントへ記載しない

PINは社員マスタに平文保存されません。

## 3. PINを忘れた場合の連絡先

ログイン後:

`設定 → PINを忘れた場合の連絡先`

から以下を設定します。

- 管理者表示名
- メール
- 電話番号
- 案内文

ログイン画面の「PINを忘れた場合」から、社員は連絡先の確認と再発行依頼を行えます。

## 4. 各社員の認証準備

`設定 → 認証設定`

で社員ごとに仮PINを発行します。

- 仮PIN利用者は初回ログイン時にPIN変更必須
- PIN未設定社員はログイン不可
- 5回失敗で一時ロック
- 管理者はロック解除可能

## 5. 権限

- `ADMIN`: 管理・社員・承認・会社カレンダー編集
- `CALENDAR_EDITOR`: 会社カレンダー編集
- `MANAGER`: 自分の操作 + 直属部下の申請承認・月次閲覧
- `USER`: 会社カレンダーは閲覧のみ

サーバー側でも権限を再検証します。

## 6. 本番公開

初期ADMIN PIN設定前に公開範囲を広げないでください。

初期設定・管理者連絡先・社員仮PINの準備後にWebアプリのアクセス範囲を変更します。無料Googleアカウント運用では、匿名公開ではなくGoogleログイン済みユーザーを対象とし、その上でFM WORKSの社員ID + PIN認証を行う構成を推奨します。

GitHubを正本とし、Apps Scriptエディタでの直接修正を常態化させないでください。


## 8. 給与集計対象とプロジェクト

### 給与集計対象

社員編集画面の「給与集計対象」をONにした社員だけが、管理者の「給与対象を一括出力」に含まれます。
要確認勤怠が残っている場合は一括出力を停止し、誤った提出を防ぎます。

### プロジェクトマスタ

工数は自由入力ではなく、設定画面のプロジェクトマスタに登録された「進行中」案件から選択します。

- 進行中: 新規工数を登録可能
- 停止 / 完了: 新規工数では選択不可
- 過去に登録済みの工数は、元の案件が停止 / 完了でも修正可能

### 有給

有給残日数は初期仮値を持たせません。管理者が実残数を設定するまで「未設定」と表示し、有給承認を停止します。
0.25日単位まで保持します。


## 9. 本番運用チェック

設定画面の「本番運用チェック」で、公開前に以下を確認します。

- 有効なADMINが1名以上いる
- 在籍社員のPINが全員設定済み
- PIN再発行用のメールまたは電話番号が設定済み
- 会社カレンダーが今後90日分登録済み
- 就業規則に沿った「法定休日」が会社カレンダーへ明示されている
- 給与集計対象者が設定済み
- バックアップが実施され、コピー整合性が検証済み
- 試作版共通PINモードが終了している

試作版では `FM0001〜FM0005 / PIN 000000` を利用できますが、本番運用では設定画面から社員ごとのPINを設定し、最後に「試作モードを終了」を実行してください。終了時には既存セッションも無効化されます。

## 10. 月次確認の追加チェック

月次画面では次の異常を表示します。

- 出勤または退勤の不足
- 会社カレンダー未登録
- 休暇・欠勤日に打刻がある
- 法定休憩の不足
- 実働時間と工数入力時間の差異

休憩時間は、労働時間が6時間を超える場合45分以上、8時間を超える場合60分以上を確認対象とします。就業規則や個別の勤務制度がこれより厳しい場合は、会社側のルールを優先してください。

## 11. 会社カレンダー

会社カレンダー画面には、実際に登録済みの年度だけを表示します。

未作成の翌年度は自動表示せず、編集権限者が「＋ YYYY年を作成」を実行した時点で初めて登録・表示します。標準生成後は、会社独自休日・年末年始・調整出勤日を管理者が確認してください。標準生成は「法定休日」を自動推測しません。就業規則の週休日・4週4休等の定めに合わせて、対象日を必ず「法定休日」として明示設定してください。

## 12. バックアップ

FM WORKS DBのバックアップ保持期間は90日です。
バックアップ作成後は、コピーを再オープンして全シートの存在・最終行・最終列を原本と照合します。整合性確認に失敗したコピーは成功扱いにしません。
バックアップとは別に、勤怠・申請・監査ログなどの本体データは削除せず履歴を保持する運用としてください。

復元試験は実運用開始前および定期的に別DBへ実施し、実際に開ける・必要シートがある・代表的な月次データを読めることまで確認してください。


## 13. ログイン状態の保持

ログイン画面の「この端末でログイン状態を保持する（30日）」をONにすると、同じブラウザ・同じ端末ではタブやブラウザを閉じてもログイン状態を再利用します。

- 保持期間: 最大30日
- 明示的にログアウトした場合は即時無効
- PIN変更・社員無効化・試作モード終了などでセッションが失効した場合は再ログイン
- 共有PCではチェックを外す
- ブラウザのサイトデータを削除すると再ログインが必要

チェックを外した場合は従来どおりブラウザセッション内だけ保持します。


## 14. 月初の先月勤怠確認

毎月1日以降、前月の本人確認が未完了の場合は、アプリ上部と通知メニューに確認アラートが表示されます。

1. 「先月の勤怠を確認」を押す
2. 月次カレンダーで赤・黄の付いた日を確認
3. 必要なら打刻修正申請または工数修正を行う
4. 要確認・工数差異が0件になったら「内容に誤りなし・確認完了」を押す

既定期限は毎月5日です。期限後は注意表示を強くします。
確認後に対象月の打刻・工数・申請・会社カレンダーが変更された場合は再確認になります。

設定シートの `MONTHLY_REVIEW_START_MONTH` は、本人確認運用を開始した年月を `YYYY-MM` で保持します。現行環境は `2026-09` です。月が変わっても、この開始月以降の未確認月は消えず、古い月から順に案内されます。

## 15. 設計文書

ADMINは `設定 → 要件定義書` と `設定 → 技術設計書` から現在の設計を確認できます。

正本はGitHubの次の2ファイルです。

- `docs/REQUIREMENTS.md`
- `docs/TECHNICAL_DESIGN.md`

`src/**` を変更する場合は、同じ変更範囲で両文書も必ず更新してください。GPT環境のローカル検証が文書同期を検査し、更新不足を検出します。

## 16. ライト / ダーク

トップバーのテーマボタンでライト・ダークを切り替えます。

- 初回はOSのテーマを参照
- 選択後はブラウザに保存
- 切替時は約0.5〜0.7秒で色とグラデーションが移行
- OSで「視差効果を減らす」等が指定されている場合は演出を抑制


## 17. 体感速度と初期表示

v0.8.2以降はログイン後の表示を2段階に分けています。

1. 先に本日の勤怠・今日の予定・基本メニューを表示
2. 月次勤務時間・残業・有給・やること・月次確認アラートをバックグラウンド取得
3. その後に予定表、工数、申請、月次、会社カレンダー、管理情報を順次先読み

ホームの集計欄に短時間スケルトンが表示されることがありますが、その間も打刻やメニュー移動は可能です。

管理者向けの自動バックアップ確認と保守情報は初回表示を止めず、「運用設定」を開いた時に必要な情報を取得します。


## 18. ライブ勤怠とショートカット

勤務中はホームと勤怠画面の「実働」がページ再読込なしで進みます。休憩中と退勤後は増えません。

ホームの月次集計に失敗した場合は、読み込み表示のまま止まらず「再読込」ボタンが表示されます。

デスクトップでは以下を利用できます。

- `/`: グローバル検索へ移動
- `Esc`: モーダル、検索結果、通知、プロフィールメニュー、モバイルドロワーを閉じる


## 19. ホームの1画面表示

v0.8.4以降、PCのホームはページ全体をスクロールしなくても主要情報を確認できる3カラムダッシュボードです。

- 上段: 日付・勤務区分・今月勤務・残業・有給残
- 左: 現在の勤怠・打刻操作・勤務場所・打刻履歴
- 中: 今日の予定
- 右: やること・工数/申請/月次のショートカット

予定や打刻履歴が多い場合は、そのカードの中だけをスクロールします。画面幅900px以下では無理に1画面へ詰めず、1カラム表示に切り替えます。

## 20. 年次有給休暇管理簿

管理者は `社員 → 対象社員 → 年休` から年休台帳を確認します。

- GRANT: 年休付与
- EXPIRE: 失効
- ADJUST: 残数調整
- USE / RESTORE: 承認・取消時に自動記録
- 10日以上のGRANTを基準に年5日取得状況を監視
- 全日有給は1日、午前/午後半休は0.5日として集計
- 1/4日有給は会社規程上の区分が確定するまで年5日の法定取得実績へ算入しない

年休付与時は残数だけを書き換えず、必ずGRANTとして付与日と日数を登録してください。付与記録がない場合、FM WORKSは年5日の対象期間を推測せず「判定材料不足」とします。

## 21. 承認経路変更

MANAGER / ADMINに直属部下がいる場合、その社員を承認権限のないロールへ降格したり退職扱いにしたりする前に、部下側の「直属承認者」を別のMANAGER / ADMINへ変更してください。

循環する承認関係（A→B→A、A→B→C→A）は保存できません。


## 22. 経理・DBの本番運用前確認（v0.13.1）

1. 管理者でログインし、「管理 → 運用」からDB状態を確認します。
2. 経理用「経費記録」「経費精算申請」「出張報告」がなければ、管理者がバックアップと検証後にDB更新を実施します。コード配信だけではシートは作られません。
3. 経理以外の社員・通常MANAGERが経理画面と保存・承認APIにアクセスできないことをテストします。
4. 架空社員で経費申請・出張報告、担当者による差戻し、本人による再申請、担当者による承認・精算を確認します。
5. 同じ証憑整理番号を経費記録と精算申請に登録し、一致／差額表示を確認します。レシート原本は別途保存が必要です。
6. GPTローカル検証成功と本番GAS公開完了は別判定です。本番画面・実端末確認は配信後に実施します。


## 23. 事務・経理の実環境確認（v0.13.3）

1. 管理者でGASアプリを開き、事務の6つの業務カード・新規申請・要対応・最近の記録を確認する。
2. 経理用DB未初期化のときは数値を表示せず初期設定を案内する。DB変更は管理者のバックアップ付き操作でのみ行う。
3. 架空の経費精算・出張・経費記録で、左の業務選択→中央の検索可能な一覧→右の詳細と承認・差戻し・精算を確認する。
4. 通常MANAGER（経理・総務以外）で事務を開き、経理の機密金額・レコード・取引先が出ないことを確認する。
5. PC／タブレット／スマホ、ライト／ダークで横はみ出しと入力可能性を確認する。実行版のGASデプロイ完了まで確認する。


## 24. 見積書の正式運用準備（v0.14.0）

1. GitHub CIとGAS公開の更新を確認後、実際の FM_WORKS_DB_ID と環境を確認する。
2. 管理者で既存FM WORKS DBのバックアップを確認し、管理→運用→DB更新でv11の見積4シートを新規作成する。
3. 管理者で「見積」を開き、元のベンダーコード(1).xlsxのSheet1 A～D列（ヘッダーは除外しても可）を貼り付けて「取引先を取り込む」を実行する。
4. 既存の見積Excelを調べて各ベンダーの最後の4桁番号を確認。推測で0を登録せず、間違いがない場合のみ「採番を確認」を実行する。
5. 架空データで社員の見積下書き→編集→正式発行→PDFとExcelの取得をテストし、税額、体裁、銀行口座、原本との差異を目視確認する。
6. 他社員の見積・PDF・Excelを閲覧できないことと、工数/勤怠/有給/経理の既存機能を確認する。
7. 8%・非課税・複数税率および納品/請求/注文/領収書の発行は対象外。原本Excelとセル単位の完全一致も対象外。

### プロジェクト詳細管理（v16）の有効化
1. **公開しただけでは新しい管理シートは作成されません。** 管理者でGASへログインし、「管理・設定 → 運用・労務 → DBスキーマ更新」を開く。
2. 既存DBのバックアップが作成・検証できることを確認してから更新する（Schema.gs version 16）。工数既存15列などのデータを消去しない。
3. 6つの追加シートの見出し、DB_VERSION=16、既存案件と工数データの保持を確認。
4. 案件詳細の「詳細管理」タブを開き、対象の案件責任者・担当社員・ADMINで権限を検証する。
5. 添付はGASデプロイ実行者のGoogle Driveの非公開フォルダ「FM WORKS - Private Project Attachments」に保存される。公開リンクを作成しない。アップロードは1.5MiB以下に制限し、ウイルス検査済みと判断しない。
6. 工数の新規登録時は「関連する作業」を選べる。過去記録は自動紐付けされず、確認してから編集で選択する。
7. 本番のログイン済み実操作・読み込み速度・ブラウザー拡大縮小・保存・既読の確認は Issue #72 に証跡を記録。

### プロジェクト読み込み時間の実測（v0.20.1）
- 管理者で「プロジェクト → 管理者ダッシュボード → プロジェクトの通信速度を確認する」を開く。案件一覧／案件詳細／詳細管理／案件保存の**実際に発生した通信**を計測する（閲覧そのものでは追加通信しない）。
- P50は1件以上で参考表示。P95は同じ操作を20回以上行った場合のみ表示する。GASの初回起動と通信キャッシュを混同しないため、冷間・再表示、回線・機種・時刻を分けてIssue #72へ記録する。
- ログアウトすると測定標本は消える。取得値はブラウザーメモリ内のみであり、権限別の数値や社員名は保存しない。
- 6シート不足が管理者のプロジェクト一覧・詳細管理画面に表示された場合は「運用・労務でDB更新」を選択し、バックアップ付きの管理者専用操作でv16へ更新する。DBを外部から直接書き換えない。

### スキーマ更新の復旧と再実行（v0.20.2）
- 管理者以外はDBスキーマ更新を実行できない。既存非空列名が一致しない場合は更新を中断し、バックアップや新規シートを作らず、列名の差を管理者が確認する。
- 最初にバックアップの検証が行われる。バックアップ失敗時はDB_VERSIONもシートも変更しない。途中で新規シート作成が失敗した場合はDB_VERSIONが古いままなので、原因解消後にバックアップを再取得して同じ更新操作を再実行する。
- 更新した結果がv16でも、監査ログの記録に失敗した場合は「DBは更新済みですが監査ログを記録できませんでした」と表示する。更新を繰り返すのではなく、監査ログとバックアップを管理者が確認する。
- 新シート作成と実際の登録・保存操作は別工程。本番の操作証跡・性能計測をIssue #72へ残す。
