# FM WORKS 実用化・速度改善 受入監査（2026-10-14）

> 正本: GitHub `Te-tsu-ya/FM-WORKS`。コード改善とGAS公開・DB更新・実ログイン/速度計測は別々の作業。**この文書は公開済み・本番合格の証明ではない。**

## 目的と検証範囲

- 目的: 社員が勤怠、工数、予定、申請を安全に毎日利用し、管理者が月次、見積、経理、資金繰り、総務、社内文書、案件を実際に保存・閲覧できること。
- 今回のコード基準: v0.25.9、PR #139。GitHub Actions/課金ランナー禁止。ユーザー指定によりGASデプロイは別のWork1チャットが担当。
- 実データ、個人情報、元Excel、DBスキーマ、既存WebアプリURL/公開範囲を変更しない。架空データの検証は既存のローカルデモと隔離したテストに限定。
- 優先原則: 認証・閲覧範囲・保存結果・監査を犠牲にして高速化しない。誤った0件/残高/有給残を出すより「未確定」と表示する。

## 高速化の判断

| 方針 | 評価 | 理由と受入 |
| --- | --- | --- |
| 不要な再通信をなくす | 採用 | 空案件マスタの正常な0件も取得済みとして5分再利用。画面の再訪・日付移動で重複通信なし |
| Sheetsの本文転送を削る | 採用 | 社員ID/日付/作業IDで正本を絞り、最大8読取窓。範囲が広ければ一括取得 |
| 短い安全な共有キャッシュ | 採用 | 総務表示20秒。容量超過や部分欠損時は正本へ戻り、認証は毎回実施 |
| 操作画面を隠す全面ローディング | 非採用 | 読取中は旧データの確認と操作を原則維持。保存時だけ適切に入力/遷移を抑止 |
| 全メニュー同時先読み | 非採用 | 未使用APIがGASの同時接続と起動を奪う。利用者の選択した画面を優先 |
| 業務/認証の長期ブラウザーキャッシュ | 非採用 | 権限変更・勤怠/会計の整合性を損なう可能性がある |
| GAS/Sheetsから他基盤への全面移設 | 要設計判断 | 多人数・大規模同時処理の実測次第。現時点で既存DBを勝手に移行しない |

一次資料: https://developers.google.com/apps-script/guides/support/best-practices ／ https://developers.google.com/apps-script/guides/html/communication ／ https://developers.google.com/apps-script/reference/cache/cache

## Work1担当：反映後の速度測定手順

1. PR #139のGitHubコードがレビュー・検証済みでmainへ統合されたことをコミットSHAで確認する。未統合featureをGASへ手動で混在反映しない。
2. Work1から既存のGASデプロイを更新し、GASのソース全文/版・公開URLの表示版・認証・DBスキーマを**別々に**照合する。公開範囲を「自分のみ」から勝手に拡大しない。
3. 管理者アカウントでログインし「管理 → 通信速度」を開く。**タブ再読込**で計測を開始し、以下を再現する。PIN・トークン・実データは画面画像や報告に出さない。
4. 最初のページを開く（冷間）、同じメニューへ戻る（暖機）。勤怠の本日/月次、工数の前後日/前後月、予定の前後月、総務/経理/資金繰りの往復を各20回程度測る。最初の1回と暖機後を分ける。
5. 「管理 → 通信速度」で処理名ごとの通信回数・失敗・P50・P95・直近値を記録する。1回/少数回のP95を安定した結果とみなさない。重複通信抑制回数も記録する。
6. 実時間とは別にGASの実行ログ `FM_WORKS_PERF`（個人情報のない集計）を確認し、ボトルネックがネットワーク/認証/シート本文/再描画のどこか切り分ける。
7. ライト/ダーク、Windows・Mac・iPad・スマホで主要機能が実操作できることを確認する。エラー・長い読取は自動無限再試行にせず、明示的な再読込を使う。
