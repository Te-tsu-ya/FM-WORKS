# FM WORKS 要件定義書

**文書版:** 0.10.3  
**更新日:** 2026-10-07  
**正本:** GitHub `docs/REQUIREMENTS.md`

## 1. 目的

FM WORKSは、社員の勤怠、工数、予定、申請、会社カレンダー、月次確認、管理を一つのWebアプリに統合する社内向けワークポータルである。

本書は、別のエンジニアが本書と技術設計書だけを読み、同等機能を再実装できる粒度で機能要件・業務ルール・画面要件・非機能要件を定義する。

## 2. 対象ユーザーと権限

| ロール | 主な権限 |
| --- | --- |
| USER | 自分の勤怠、工数、申請、月次確認。共有予定表・会社カレンダー閲覧 |
| CALENDAR_EDITOR | USER権限 + 会社カレンダー編集 |
| ADMIN | 全機能。社員・認証・承認・プロジェクト・運用設定・設計文書閲覧 |

管理系APIは画面制御だけに依存せず、Apps Script側で必ず再認証・再認可する。

## 3. 画面構成

### 3.1 共通ナビゲーション

左サイドバーに以下を表示する。

- ホーム
- 勤怠
- 工数
- 予定表
- 会社カレンダー
- 申請
- 社員
- 月次
- 設定（ADMINのみ）

ADMINの設定配下に以下のサブメニューを表示する。

- 運用設定
- 要件定義書
- 技術設計書

### 3.2 1画面完結方針

- PCではホーム・月次・設定を1ビューポート内に収める。
- 情報量が多い表・文書はページ全体ではなくパネル内スクロールを使う。
- スクロールしなければ主要操作に到達できない構造を減らす。
- モバイルは画面幅の制約を優先し、必要な場合のみ縦スクロールを許容する。

### 3.3 クリック視認性

- ボタン、カード、日付セル、セレクト、ナビ、クリック可能行はポインタカーソルを表示する。
- 独立したポインタ操作対象は原則24×24 CSS px以上を確保し、小型ボタンは28px以上を基本とする。
- ホバー時に背景・枠・影のいずれかが変化する。
- キーボード操作時は `:focus-visible` を明確に表示する。
- 色だけで状態を伝えず、文言・アイコン・バッジを併用する。

### 3.4 ホーム

PCのホームは縦積みカードではなく、1画面の業務ダッシュボードとして構成する。

上段「コマンドバー」:

- 挨拶
- 当日の日付
- 会社カレンダー区分
- 今月の勤務時間
- 今月の残業
- 有給残

下段は3カラム:

1. **現在の勤怠**
   - 勤務状態
   - 出勤 / 実働 / 退勤
   - 出勤・休憩・退勤操作
   - 勤務場所
   - 当日の打刻履歴
2. **今日の予定**
   - 時刻
   - 件名
   - 参加者名
   - 場所
   - 詳細な予定表への導線
3. **やること**
   - 工数
   - 勤怠確認
   - 申請/承認
   - 工数・申請・月次へのクイック導線

PCではページ全体を縦スクロールさせず、件数が多い予定・打刻履歴だけカード内部でスクロールする。

高さ760px以下の広いPCでは余白・フォント・パネル内間隔を圧縮する。画面幅1140px以下では3カラムを無理に詰めず、ホームだけ1画面固定を解除して1カラムの通常スクロールへ切り替える。

## 4. ライト / ダークテーマ

- ライト、ダークの2テーマを提供する。
- 初回はOSの `prefers-color-scheme` を参照する。
- 以後はユーザーが選んだテーマを `localStorage` に保存する。
- 切替時は約0.5〜0.7秒かけて色・背景・グラデーションが滑らかに移行する。
- 対応ブラウザではView Transition APIを利用し、非対応ブラウザはCSSトランジションへフォールバックする。
- `prefers-reduced-motion: reduce` の場合は大きな演出を抑制する。

## 5. 認証

### 5.1 ログイン

- 社員ID + 6桁PIN。
- 試作モードでは架空社員 `FM0001〜FM0005` のみ共通PIN `000000` を許可できる。
- 本番モードでは社員ごとのPINのみ。
- 「この端末でログイン状態を保持する」をONにした場合は最大30日保持する。

### 5.2 PIN保護

- PIN平文保存禁止。
- 社員別Salt + Script Properties上のPepper。
- HMAC-SHA256でハッシュ化。
- 失敗回数制限と一時ロック。
- 仮PINは初回変更必須。

### 5.3 セッション

- ブラウザには生トークン。
- DBにはトークンハッシュのみ。
- absolute expiry / idle expiryを持つ。
- ログアウト、PIN変更、社員無効化、試作モード終了時に失効する。

## 6. 勤怠

- 勤務中の「現在の実働」は初回取得値で止めず、サーバー時刻を基準にブラウザ上で継続更新する。
- 休憩中・退勤済みは実働時間を増加させない。
- 打刻直後はサーバーから返る時刻を新しい基準時刻として採用する。


### 6.1 打刻種別

1. 出勤
2. 休憩開始
3. 休憩終了
4. 退勤

勤務場所は `出社 / 在宅 / 外出`。

### 6.2 打刻順序

サーバー側で順序検証を行う。

- 退勤前に出勤が必要。
- 休憩終了前に休憩開始が必要。
- 重複出勤など不正遷移を拒否する。

### 6.3 打刻修正

- 元打刻を物理更新・削除しない。
- 修正レコードを追加する。
- 元打刻IDとの関係を残す。
- 承認操作と監査ログを必須とする。

### 6.4 休憩チェック

- 実働6時間超: 45分以上。
- 実働8時間超: 60分以上。
- 不足は月次の要確認理由にする。

## 7. 月初の先月勤怠確認

### 7.1 自動アラート

- 毎月1日以降、前月の本人確認が完了していない社員へアラートを出す。
- アラートはホームだけでなく全画面上部に表示する。
- 通知メニューにも「勤怠確認」を出す。
- 確認完了するまで継続表示する。
- 月が変わっても未確認月を消さず、`MONTHLY_REVIEW_START_MONTH` 以降の未確認・再確認月を古い順に案内する。
- 1つの月を確認完了した後、未確認月が残っていれば次の対象月を自動表示する。
- `MONTHLY_REVIEW_DUE_DAY` の既定値は5日。
- 1日〜期限日はwarning。
- 期限超過後はdanger。

### 7.2 再確認

確認後に対象月の以下が更新された場合は、確認済みを再確認状態として扱う。月をまたいでも再確認義務を失わない。

- 打刻
- 工数
- 申請
- 会社カレンダー

### 7.3 確認完了条件

本人が自分の過去月を確認する。

確認完了ボタンは以下が0件の場合だけ有効。

- 要確認日
- 工数差異日

ADMINが月次画面で他社員を選択した場合、その社員の本人確認状態を読み取り専用で表示する。ADMINが本人確認を代理完了することはできない。

確認時に以下を記録する。

- 年月
- 社員ID
- 氏名
- 状態
- 確認日時
- 確認者
- 確認時最終更新
- メモ
- 登録日時
- 更新日時

## 9. 工数

- 進行中プロジェクトから選択。
- 作業内容必須。
- 開始・終了必須。
- 同一社員・同一日の重複時間帯禁止。
- 削除はソフトデリート。
- 月次締め済み月は追加・編集・削除禁止。
- 実働との差が5分超の場合は月次で工数差異。

## 10. 予定表

- 月 / 週 / 日 / 一覧。
- 予定カードに社員名を直接表示。
- 社員色は補助情報。
- カテゴリ色とは分離。
- 複数人は先頭2名 + 残人数。
- 色だけで担当者を判断させない。

## 11. 会社カレンダー

- 登録済み年度だけ表示。
- 未作成年度は自動表示しない。
- 権限者が「YYYY年を作成」を押した時点で生成。
- 初期生成は土日・国民の祝日。
- 会社独自休日・年末年始・調整出勤日は人が確認して修正。

## 12. 申請

申請種別:

- 有給
- 午前半休
- 午後半休
- 1/4日有給
- 欠勤
- 打刻修正
- 在宅勤務
- 残業
- 休日出勤

画面要件:

- 「何を申請しますか？」のクイックカード。
- 選択後は必要項目だけ表示。
- 有給系は現在残 / 承認待ち / 申請可能残 / 今回消化 / 申請後残数。
- エラーはフォーム内に具体的に表示。
- エラー項目へフォーカス。
- Toastは補助に留める。

## 13. 有給

- 有給残日数は0.25日単位。
- 実値不明なら仮値を設定しない。
- 未設定は明示。
- 承認待ち分を申請可能残から差し引く。
- 不足する申請は申請前に拒否する。

## 14. 月次締め

ADMINのみ。

締め前条件:

- 給与対象者1名以上。
- 要確認勤怠0。
- 工数差異0。
- 承認待ち申請0。

締め後:

- 工数追加・編集・削除停止。
- 対象月の申請承認停止。

解除:

- ADMINのみ。
- 理由必須。
- 監査ログ必須。

## 16. 設定

ADMINの設定画面をタブ化する。

- 認証・サポート
- プロジェクト
- 運用設定
- 要件定義書
- 技術設計書

プロジェクトタブでは、既存プロジェクトの一覧・編集と新規追加を行えること。設定画面の再構成によってこの機能を失わないこと。

### 16.1 要件定義書・技術設計書

- ADMINのみ閲覧可能。
- GitHub Markdownを正本とする。
- デプロイ時にApps Script用データへ生成。
- アプリ内で見出し、表、リスト、コードを読みやすく表示。
- 「再読込」はクライアントキャッシュを無視し、現在のデプロイ文書を再取得する。

## 17. 文書同期ルール

- `src/**` の変更を伴うコミットは、同じコミットで `docs/REQUIREMENTS.md` と `docs/TECHNICAL_DESIGN.md` の両方を更新する。
- GitHub Actionsで検査する。
- 片方でも未更新ならデプロイ失敗。
- 文書版と `APP.version` を一致させる。
- UI変更、業務ルール、データ構造、API、セキュリティ、運用変更はすべて文書反映対象。

## 18. 性能

- ログイン直後は「認証・本日の勤怠・今日の予定・会社カレンダー当日・社員/プロジェクトマスタ」を先に返し、月次集計・申請件数・月次本人確認はホーム概要として非同期取得する。
- 初期表示API `getInitialData` では `getMonthlySummary` と申請全件取得を実行しない。
- ホーム概要の読込中は画面全体を止めず、やること・月次指標だけスケルトン表示する。
- ホーム概要の取得に失敗した場合、スケルトンを残し続けず、画面内に失敗理由と「再読込」を表示する。
- ホーム概要完了後、全画面の月次確認コーションだけを独立更新できる。
- 打刻や月次確認の直後にホーム概要の再取得要求が重なった場合、先行通信の古い結果で新しい状態を上書きせず、完了後に強制再取得する。
- メニュー切替はキャッシュ済み画面を即時表示する。
- ログイン直後の先読みは、ホーム概要・現在表示ページを優先し、その後に予定表→工数→申請→月次→会社カレンダー→管理情報の順で段階実行する。
- 通知取得、自動バックアップ確認、管理画面保守情報は初回描画をブロックしない。
- 管理画面の保守情報は「運用設定」タブを表示した時だけ取得する。
- 重複通信を抑止する。
- Google Sheets呼び出しは一括読込・一括書込を優先する。
- Apps Scriptサービス呼び出し回数を最小化する。

## 19. エラー

- セッション切れ: ログインへ戻す。
- 一般操作: Toast。
- 入力: モーダル内エラー。
- 具体的な業務理由を表示。
- 色だけに依存しない。

## 20. バックアップ

- DBバックアップ保持90日。
- 管理者利用時に1日1回を基本。
- 手動バックアップ可能。

## 21. 受入条件

1. 月初に前月未確認アラートが全画面で表示される。
2. 確認完了後に対象月のアラートが消える。
3. 確認後のデータ変更で再確認アラートが表示される。
4. 月が変わっても古い未確認月が消えず、最古の未確認月から順に案内される。
5. 月次をカレンダーで確認できる。
6. 日付から打刻修正または工数確認へ移動できる。
7. ADMINだけが要件定義書・技術設計書を読める。
8. ソース変更コミットで両設計文書が未更新ならCIが失敗する。
9. ライト・ダークの選択が保存される。
10. テーマ切替が滑らかに見える。
11. PCの月次・設定は長いページ全体スクロールを必要としない。
12. クリック可能箇所はポインタ・ホバー・フォーカスを持つ。
13. 既存機能に回帰がない。
14. 設定 → プロジェクトで一覧・追加・編集が正常に動作する。
15. ADMINが他社員の月次本人確認状態を確認できる。
16. 設計文書の「再読込」が実際にサーバーから再取得する。
17. ログイン後の初期画面は月次集計・申請全件取得を待たずに表示される。
18. ホーム概要を読み込み中でも勤怠打刻・メニュー移動が可能である。
19. 設定の認証・プロジェクトタブでは保守情報APIを不要に取得しない。
20. ホーム集計失敗時は画面内から再読込できる。
21. 勤務中の実働時間がページ再読込なしで進む。
22. Escでモーダル/補助UIを閉じられ、デスクトップでは `/` で検索へ移動できる。
23. 1141px以上のPCホームはページ全体をスクロールせず、主要情報と操作が1画面に収まる。
24. 予定・打刻履歴が多い場合は該当カード内部だけがスクロールする。
25. 1140px以下では横幅不足による潰れを避けるため、ホームだけ1画面固定を解除して読みやすい1カラムへ戻る。


## 22. 承認階層と職務分掌

社員権限に `MANAGER` を追加する。

- USER: 自分の勤怠・工数・予定・申請
- CALENDAR_EDITOR: USER + 会社カレンダー編集
- MANAGER: USER + 直属部下の申請承認 + 直属部下の月次閲覧
- ADMIN: 全体管理。ただし自分自身の申請は承認不可

社員マスタX列 `直属承認者ID` を使用する。

承認条件:

1. 申請者と承認者が同一人物なら必ず拒否する。
2. MANAGERは `直属承認者ID === 自分の社員ID` の社員だけ承認できる。
3. ADMINは他社員を承認できるが、自分自身は承認できない。
4. 権限判定はサーバーAPIで再検証する。
5. MANAGERの月次社員選択肢は自分 + 直属部下だけ。
6. 月次締め・一括給与出力・社員設定はADMINのみ。

### 22.1 追加受入条件

- 自己承認APIは失敗する。
- MANAGERが非直属社員を承認しようとすると失敗する。
- MANAGERがURL/APIから非直属社員の月次を指定しても失敗する。
- MANAGER画面には月次締めと給与一括出力を表示しない。


## 23. 月次締め確定スナップショット

月次締めは単なる `CLOSED` フラグではなく、締め時点の給与対象社員の月次・日次値を確定スナップショットとして保存する。

- `月次確定`: 社員別月次合計、締め日時、締め者、SHA-256データハッシュ
- `月次確定日次`: 日付ごとの出退勤、実働、残業、休日勤務、遅刻早退、休憩、工数、勤務場所、休暇、要確認
- `月次締め`: 使用したスナップショットIDを保持
- 締め済み月の個人Excelは確定スナップショットから作成
- 給与対象一括Excelは月次締め後のみ作成可能で、確定スナップショットを使用
- 締め解除後の再締めは新しいスナップショットIDを発行し、過去スナップショットは削除しない

これにより「同じ締めIDなら同じ給与根拠値」を再現できること。


## 24. 有給台帳と承認済み取消

有給残日数は社員マスタの単一数値だけで管理しない。社員ごとに有給台帳を保持する。

有給台帳は少なくとも以下を保持する。

- 年休基準日
- 取引日
- 種別: OPENING / GRANT / USE / RESTORE / EXPIRE / ADJUST
- 増減日数
- 取引後残日数
- 関連申請ID
- 処理者
- 処理日時
- 備考

社員設定で有給残を初めて設定する場合、年休基準日を必須とする。以後の管理者による残数変更はADJUSTとして履歴化する。

有給承認はUSE、承認済み有給の取消承認はRESTOREを記録し、社員マスタの有給残は表示用キャッシュとして同期する。

承認済み申請は本人が取消理由を入力して「取消申請中」にできる。元の承認者権限範囲にある別人が取消承認/取消却下を行う。承認済み打刻修正は直接巻き戻さず、新しい打刻修正申請で訂正する。

年休台帳の法令上の保存要件・年5日取得義務などは会社ルールと法令設定を別途実装し、未設定の段階で「法令対応済み」と表示しない。


### 24.1 Export API認証

月次Excelの公開APIは入口で認証済みセッションを必ず検証し、内部の確定スナップショット参照へ処理を委譲する。


## 25. 予定の公開範囲

予定は `社内 / 参加者のみ / 管理者のみ` を選択できる。公開範囲はサーバーで強制し、予定表とグローバル検索の双方で同じ認可を適用する。非ADMINは `管理者のみ` を作成できない。


## 26. 実行環境とDB分離

実行環境は `DEVELOPMENT / STAGING / PRODUCTION` のいずれかとする。

- Script Property `FM_WORKS_ENVIRONMENT` 未設定時はSTAGING。
- DEVELOPMENT/STAGINGは既定DBへフォールバック可能。
- PRODUCTIONは `FM_WORKS_DB_ID` の明示設定を必須とする。
- PRODUCTIONでSTAGING既定DBを再利用することは禁止する。
- システム状態に現在の実行環境を表示する。
- 本番運用チェックはPRODUCTION以外を未完了として扱う。
- 試作PIN終了と実行環境昇格は別工程とし、誤って本番設定へ切り替わらないようにする。


## 27. 自動バックアップ時間トリガー

DBバックアップは管理者のログイン有無に依存させない。

- 毎日03時台にApps Script時間トリガーから実行する。
- 同じ日に既に成功していればスキップする。
- Script Lockで重複実行を防止する。
- 有効化時は時間トリガーを1件だけ作成する。
- 無効化時は対象トリガーを削除する。
- 管理画面からトリガーを再設定できる。
- 成功/失敗を監査ログへ記録する。
- 保持期間は90日。


## 28. 労務計算モデル v0.9.6

所定外時間と法定区分を分離する。法定日次時間外は1日8時間超、法定週次時間外は日次時間外との二重計上を避けて週40時間超を算出する。深夜労働は22:00〜05:00、法定休日労働は会社カレンダーで明示した「法定休日」の実働とする。

`LABOR_RULE_PROFILE=UNCONFIGURED` の間は一般則ベースの参考値として表示し、本番READYと月次締めを禁止する。管理者が就業規則・36協定を確認し、GENERAL_JPと週開始曜日を保存して初めて設定済みとする。

月45時間超、月60時間超、法定時間外＋法定休日労働が単月100時間以上を注意表示する。年360時間、複数月平均80時間、変形労働時間制、フレックス、業種特例、会社固有の特別条項は今後の会社固有設定で扱い、現段階で「法令適合」と自動判定しない。

受入条件:
- 会社カレンダーで法定休日を明示できる。
- 月次で法定時間外・深夜・法定休日労働を確認できる。
- 月境界をまたぐ週も週40時間判定に前後日を含める。
- 未設定状態では本番READYと月次締めを拒否する。
- 締めスナップショットに法定区分を保存する。


## 29. 監査証跡 v0.9.7

重要マスタ・業務データの更新は、状態名だけでなく変更前/変更後の主要フィールドを監査ログへJSONで保存する。

対象:

受入条件:

## 31. 日付スコープI/Oと性能予算 v0.9.9

日付範囲が既知の打刻、工数、会社カレンダー、月次更新判定では、原則として全行を読み込んでから破棄しない。

`readRowsByDateRange_` は日付列をTextFinderで検索し、対象行を連続ブロック化して必要行だけ取得する。分散が大きく48ブロックを超える場合はサービス呼び出し過多を避けて全行読込へフォールバックする。

構造化性能ログ `FM_WORKS_PERF` を出力し、警告予算を月次集計3.5秒、工数1.5秒、日付範囲読込1.2秒とする。


## 32. 本番認証Fail-Closed v0.10.0

試作モードは明示設定がない場合に無効を既定値とする。

- STAGING / DEVELOPMENTでは、設定 `PROTOTYPE_MODE=TRUE` の場合に限り試作認証を許可する。
- PRODUCTIONでは、`PROTOTYPE_MODE` が誤ってTRUEのままでも共通PIN認証を強制的に無効化し、社員ごとのPIN認証だけを許可する。
- 公開認証設定APIは試作PINそのものを返さない。
- ログイン画面へ共通PINを表示しない。
- ログイン入力欄へ共通PINを自動入力しない。
- 本番運用チェックは、実効的に共通PINが無効でも設定値がTRUEならREADYにしない。

受入条件:
- TRUE + STAGING は試作モードを許可する。
- TRUE + PRODUCTION は試作モードを拒否する。
- FALSE + STAGING は試作モードを拒否する。
- Apps Script実行環境情報を取得できない単体テスト環境では試作ログインをFail-Closedする。
- CIが本番ガードとPIN非公開化を静的検査し、ロジックテストが環境境界を検証する。


## 33. フロントエンド責務分割 v0.10.1

1つの巨大なクライアントファイルへ全画面・認証・管理機能を集約しない。以下の5モジュールへ責務を分ける。

- `AppCore.html`: 状態、キャッシュ、共通UI、ナビゲーション、ホーム。
- `AppOperations.html`: 勤怠、工数、予定、会社カレンダー、申請。
- `AppPeopleMonthly.html`: 社員、月次。

- `AppShell.html`: ページ描画、ログイン、検索、通知、プロフィール、起動処理。

受入条件:
- `Index.html` が5モジュールを明示的な順番で読み込む。
- 旧 `App.html` の巨大実装は使用しない。
- CIは5モジュールを連結した状態でJavaScript構文と既存UI契約を検査する。
- 各モジュールはおおむね500行以下を維持し、今後の変更は責務に対応するファイルへ置く。


## 34. 可読性・キーボード・再描画・スクロール改善 v0.10.2

### 34.1 可読性

業務画面で意味を持つ文字は11px未満を使用しない。特に予定、月次、申請、ホーム、ログイン、管理画面の補助情報を含め、7〜10pxへ縮小して1画面へ押し込む設計を禁止する。

### 34.2 スクロール

PCで1画面固定を優先するのはホームのみとする。月次・設定・年間カレンダーはページ全体を自然にスクロールさせる。内部スクロールは予定一覧、履歴、文書など「長い一覧/長文を明示的に閲覧する領域」に限定する。

### 34.3 実働時間更新

勤務中の実働時間表示は30秒ごとに画面全体を再描画しない。`data-live-worked` を持つ実働表示ノードだけを書き換え、入力フォーカス・スクロール位置・開いている操作状態を壊さない。

### 34.4 予定表キーボード操作

月表示は各日付にキーボードフォーカス可能な「日詳細を開く」操作を提供する。日表示の予定行はネイティブbuttonとして操作可能にする。フォーカス状態は視覚的に明確に表示する。

### 34.5 モーダル

モーダル表示時はモーダル内へフォーカスを移し、Tab / Shift+Tabをモーダル内に閉じ込める。Escapeで閉じられ、閉じた後は原則として呼び出し元へフォーカスを戻す。

### 34.6 セッションGC

ログイン処理では期限切れセッション全件削除を行わない。セッションGCは日次メンテナンスへ移し、連続した削除対象行は`deleteRows`でまとめて削除する。

受入条件:
- CSSに11px未満のfont-sizeが存在しない。
- 勤務中タイマー更新関数に`renderPage()`を含めない。
- 予定表の日付・日表示予定がキーボードだけで操作できる。
- モーダルがTabフォーカスを背面へ逃がさず、閉じると呼び出し元へ戻る。
- `createSession_` はセッションGCを呼ばない。
- 日次メンテナンスがセッションGCを実行する。
- CIが上記を回帰検査する。


## 35. 36協定の年次・複数月監視 v0.10.3

日本・一般則プロファイルを「設定済み」とするには、週開始曜日に加えて次を必須とする。

- 36協定の対象期間の起算月（1〜12月）
- 特別条項の有無（なし / あり。未確認は不可）

一般則の監視値は厚生労働省が示す基準を基礎とする。

- 時間外労働: 原則 月45時間・年360時間
- 特別条項がある場合の一般則上限: 年720時間
- 時間外＋法定休日: 単月100時間未満
- 時間外＋法定休日: 2〜6か月平均80時間以内
- 月45時間を超えられる月数: 年6か月まで

年次・複数月判定は、締め済み月の月次確定スナップショットと対象月の最新集計を組み合わせる。必要な過去月の確定データが不足する場合は「判定完了」とせず、不足警告を表示する。

これらは一般則の監視支援であり、変形労働時間制、フレックスタイム制、業種別特例、個別36協定の具体的上限を自動的に法令適合判定しない。

### 35.1 1/4日有給

現行の「1/4日有給」は会社規程上の根拠が未確定である。時間単位年休として扱う場合は労使協定・対象者・単位時間等の設定が必要であり、年5日の取得義務への算入を自動推定しない。

本番化前にProduct Ownerと労務担当が制度上の位置付けを確定し、Q-026を解消する。
