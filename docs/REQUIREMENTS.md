# FM WORKS 要件定義書

**文書版:** 0.17.2  
**更新日:** 2026-10-10  
**正本:** GitHub `docs/REQUIREMENTS.md`

## 1. 目的

FM WORKSは、社員の勤怠、工数、予定、申請、会社カレンダー、月次確認、管理を一つのWebアプリに統合する社内向けワークポータルである。

本書は、別のエンジニアが本書と技術設計書だけを読み、同等機能を再実装できる粒度で機能要件・業務ルール・画面要件・非機能要件を定義する。

## 2. 対象ユーザーと権限

| ロール | 主な権限 |
| --- | --- |
| USER | 自分の勤怠、工数、申請、月次確認。共有予定表・会社カレンダー閲覧 |
| CALENDAR_EDITOR | USER権限 + 会社カレンダー編集 |
| MANAGER | USER権限 + 直属部下の申請承認・月次閲覧 |
| ADMIN | 全機能。社員・認証・他社員承認・プロジェクト・運用設定・設計文書閲覧 |

管理系APIは画面制御だけに依存せず、Apps Script側で必ず再認証・再認可する。

## 3. 画面構成

### 3.1 共通ナビゲーション

左サイドバーのトップ階層は日常業務へ絞り、以下を表示する。

- ホーム
- 勤怠
- 工数
- 予定表
- 申請
- 管理（ADMINのみ）

トップ階層から外した機能は削除せず、関連ワークスペースへ統合する。

- 勤怠: 本日 / 月間 / 履歴
- 予定表: 予定 / 会社カレンダー
- 管理: 社員・権限 / 認証・サポート / プロジェクト / 運用・労務 / 要件定義書 / 技術設計書

月次、会社カレンダー、社員管理の旧内部ルートは既存リンク互換のため維持し、左ナビ上では親メニューをアクティブ表示する。

### 3.2 1画面完結方針

- PCで1ビューポート完結を優先するのはホーム、勤怠「本日」、工数「本日」とする。
- 月次・設定・年間カレンダーは可読性を優先し、ページ全体を自然にスクロールさせる。
- 情報量が多い表・文書はページ全体ではなくパネル内スクロールを使う。
- スクロールしなければ主要操作に到達できない構造を減らす。
- モバイルは画面幅の制約を優先し、必要な場合のみ縦スクロールを許容する。

### 3.3 クリック視認性

- ボタン、カード、日付セル、セレクト、ナビ、クリック可能行はポインタカーソルを表示する。
- 独立したポインタ操作対象は原則24×24 CSS px以上を確保し、小型ボタンは28px以上を基本とする。
- ホバー時に背景・枠・影のいずれかが変化する。
- キーボード操作時は `:focus-visible` を明確に表示する。
- 色だけで状態を伝えず、文言・アイコン・バッジを併用する。

### 3.4 ホーム（個人ポータル・タスク優先型 v0.11.9）

目的：毎日最初に開くホームを、勤務状態・次の打刻・重要な対応・今日の予定がすぐ分かる画面にする。従来の3カラム固定高による空白を廃止する。

**情報の優先順位**
1. 挨拶・今日の日付・会社カレンダー区分と現在の勤務状態。朝・昼・夕方の挨拶はクライアントの時刻に応じて変化する。
2. 今月の勤務時間、残業、有給残、承認待ちの4指標。管理者・承認担当者では「チーム承認待ち」、通常社員では「自分の申請待ち」。実際の `getHomeOverview` の認可済み結果を表示し、未取得の値はローディング、取得失敗はエラーと再試行。
3. **出勤・退勤・休憩などの主要打刻**。現在状態・出勤・実働・退勤・勤務場所・当日の打刻履歴を操作可能なまま維持する。
4. **要対応タスク**。工数入力差、打刻漏れ、承認待ち等を既存APIの実データから抽出し、危険・注意順に配置。項目クリックで工数/勤怠/申請へ移動する。問題がない場合は完了案内、その他の状況は折りたたむ。偽のタスクや数値を作らない。
5. **今日の予定**。最大4件をコンパクトに表示。各予定をクリックして該当イベントへ移動。0件なら大きな空白にせず、「予定はありません」「予定を登録」の一体型カードを表示。
6. **よく使う機能**。工数、休暇・申請、月次勤怠、予定表。管理権限者には社員設定も追加する。

**画面構成**
- PC：コンパクトなヘッダー、4指標、左「出退勤→予定」、右「要対応→ショートカット」の2列。カラムごとに内容の高さに合わせ、3枚の固定高カードは使わない。ページ全体の自然スクロールを許容する。
- タブレット・スマホ：上段指標は2列にし、コンテンツは「出退勤→要対応→予定→ショートカット」の順に縦積み。横スクロール・小さすぎる文字・タッチしづらいボタンを避ける。
- ライト/ダーク、キーボードフォーカス、読み込み中・0件・失敗・操作成功時のフィードバックを維持する。
- ホーム描画に新たな GAS 呼出しを増やさない。既存 `getHomeOverview` へすでに算出した承認待ち件数を数値として付加し、前ログインの古い非同期応答は反映しない。
- 打刻・勤務場所変更・予定編集・申請・勤怠確認の既存サーバーAPIと権限チェックは変更しない。

**受入条件**
- 勤怠の全操作導線、勤務場所・打刻履歴、月次・申請・工数・予定表のリンクが維持される。
- 予定0件でも高さが固定されず、予定登録へのリンクがある。
- タスクは実データ・緊急度順で、完了済み項目は必要時だけ開く。表示切替やタスククリックに無用な再取得はない。
- 社員と承認担当者で対応ラベルが分かれる。社員情報、タスク、予定タイトルはエスケープされ、他ユーザーの古い応答は表示されない。
- 自動テスト（ドキュメント同期、構文、ロジック、クライアント契約）がすべて成功。実機でPC・タブレット・スマホの視認性も確認する。


### 3.5.1 ホームの標準PC第一画面収容・共通フォーカス v0.11.10

- 標準PCの画面例1792×850では、ホームのヘッダー・月次指標・出退勤・要対応・今日の予定・ショートカットを第一画面に収めることを設計目標とする。
- 1200px以上かつ高さ690px以上ではホームだけに限定したコンパクト余白を使う。主要な操作の文字/打刻ボタンを読めないほど縮めない。
- ブラウザの縦幅が低い場合やズーム・文字拡大時はスクロールを許可し、表示を切り捨てない。予定数・タスク数が多い場合も切り捨てず確認できること。
- 他画面の視認性を損なわない範囲で共通フォーカス可視化を追加する。全画面UI統一の現在の状態と課題は `docs/UI_UX_CONSISTENCY_AUDIT.md` を正本の監査記録とする。
- 実ブラウザで高さ・文字のクリップ・操作性を測定しない限り「PCの全条件で完全に1画面」を保証しない。

### 3.5 勤怠ワークスペース

勤怠は「本日 / 月間 / 履歴」の3タブで構成する。

**本日**は、最初の3〜5秒で「現在の状態」「次に行う打刻」「確認が必要な問題」が分かることを最優先する。

上段:
1. 現在の勤務状況
   - 勤務中 / 休憩中 / 退勤済み / 勤務外
   - 実働時間
   - 出勤・休憩・退勤操作
   - 勤務場所
2. 今日の勤務タイムライン
   - 出勤、休憩開始、休憩終了、退勤
   - 現在状態
   - 会社カレンダーに終了時刻がある場合は退勤予定
3. 確認が必要なこと / 本日の集計
   - 月次本人確認
   - 打刻問題
   - 工数差異
   - 実働、休憩、予定勤務に対する残り時間

下段:
- 当月の簡易カレンダー
- 今月の出勤日数、実働、残業、有給取得
- 直近5日程度の勤怠履歴

当月カレンダー・月間サマリー・履歴は初期打刻UIをブロックしてはならない。`getMonthlySummary` は本日画面描画後に遅延取得し、取得中も出退勤・休憩・勤務場所の操作を可能とする。

「保存先 Google Sheets」等の技術実装情報は一般社員の勤怠画面へ主要情報として表示しない。

### 3.6 勤怠本日の1画面表示と検証用サンプル

- PC幅1141px以上では、勤怠「本日」の主要領域をページスクロールなしで1画面に収める。
- 高さが低いPCでは余白・カード内パディング・タイムライン間隔を縮め、主要操作と月間プレビューを同一画面内に維持する。
- 幅1140px以下は可読性を優先し、通常の縦スクロールへ戻す。
- 実データがまだ無いADMINには、カレンダー・月間集計・直近履歴・警告状態を評価できる表示確認用サンプルをクライアント側だけで生成する。
- サンプルには正常勤務、在宅、工数差異、有給、打刻不足を含める。
- サンプルは「表示確認用サンプル」と明示し、Google SheetsやサーバーAPIへ書き込まない。
- サンプル日をクリックした場合は読み取り専用の詳細モーダルを表示し、申請・締め・Excel出力等の実データ操作へ混入させない。
### 3.7 可読性と勤務途中の勤務場所変更

#### 可読性
- 勤怠「本日」は1画面性を維持しつつ、通常利用者が読む本文・表・カレンダー・状態ラベルをv0.10.8より一段大きくする。
- 装飾目的の英字eyebrow等は情報本文より優先しない。
- トップバーに「文字サイズ：標準 / 大きめ」の切替を置き、選択を `localStorage['fmworks.fontSize']` に保存する。
- 「大きめ」では可読性を1画面固定より優先し、必要なら勤怠ページの縦スクロールを許可する。

#### 勤務場所の途中変更
- 勤務場所は `出社 / 在宅 / 外出`。
- 出勤前は勤務場所ボタンを「次の出勤打刻で使用する場所」の選択として扱う。
- 勤務中または休憩中に別の勤務場所を選択した場合、単なる表示切替ではなく「勤務場所変更」として時刻付きで打刻ログへ追記する。
- 例: `09:00 出勤（出社） → 13:30 勤務場所変更（出社→在宅） → 18:00 退勤（在宅）`。
- 勤務場所変更は実働時間・休憩時間の計算状態を変化させない。
- 退勤後の勤務場所変更は拒否する。
- 当日のタイムラインに勤務場所変更を表示する。
- 月次の日別「勤務場所」は1日の遷移を `出社→在宅` のように要約表示し、その日のどこかで在宅勤務を含めば在宅勤務日として集計する。
- 打刻修正申請の対象は従来どおり出勤・休憩開始・休憩終了・退勤とし、「勤務場所変更」を打刻時刻修正の種別へ混入させない。
- 勤務場所変更は監査ログに変更前・変更後を記録する。

### 3.8 工数ワークスペース v0.11.0

工数「本日」は、**勤怠時間に対して未入力の時間を見つけ、その場で埋める**ことを最優先する。

PC上段:
- 入力済工数
- 本日の実働
- 未入力時間
- プロジェクト数

PC中段:
1. **本日のタイムライン**
   - 工数登録済み区間をプロジェクトごとに色分け
   - 勤怠の休憩履歴がある区間は「休憩」
   - 勤怠時間内で工数が無い区間は「未入力」
   - 未入力区間をクリックすると、右側クイック入力の開始・終了へ時刻を転記
2. **クイック入力**
   - プロジェクト
   - 作業分類
   - 開始 / 終了
   - 作業内容
   - 「登録する」で既存 `saveWorklog` APIへ保存
   - 詳細な備考や既存データ編集は従来の工数モーダルを使用

PC下段:
- 本日の工数一覧
- 時間 / プロジェクト / 作業分類 / 内容 / 工数 / 状態 / 操作
- 件数が多い場合はページ全体ではなく一覧パネル内部だけをスクロール

PC幅1141px以上では、主要KPI・タイムライン・クイック入力・工数一覧を1ビューポートへ収めることを優先する。幅1140px以下ではタイムラインとクイック入力を縦積みにして通常スクロールへ戻す。

当日の実働時間は勤怠データと連携する。工数登録済み時間との差を未入力時間として表示する。現在勤務中の場合は、サーバー基準時刻から経過分を加算した実働時間を利用する。

ADMINで当日の工数実データが0件の場合、デザイン確認用としてブラウザ内だけのサンプルを表示してよい。サンプルは「表示確認用サンプル」と明示し、Google Sheetsへ保存しない。サンプルは複数プロジェクト、休憩、未入力時間を含める。実プロジェクトが無い場合、クイック入力の保存は無効化する。 サンプルのプロジェクト名は実在顧客・実案件を使わず匿名名称とする。

### 3.9 工数の日付切替高速化 v0.11.1

- 工数の日付を前日・翌日に移動する操作は、取得済みの日付なら新しい `google.script.run` を発行せずブラウザ内キャッシュから即時表示する。
- サーバーの `getWorklogs` への一回の呼び出しで約14日分（選択日を含む週と前週）を取得し、日別に抽出して表示する。既存のAPI認証と社員範囲を維持する。
- 未記録の日付も「0件」という取得済み状態でキャッシュし、空の日付を閲覧するたびに再通信しない。
- キャッシュはセッション・社員ごとに分離する。過剰なメモリ使用を防ぐため保持区間数を制限する。
- データは最大120秒を新鮮とみなし、期限後は旧データを即時描画したうえで背景更新する。
- 連続した日付操作で複数の未完了要求を並列発行せず、最新の選択日だけを描画する。
- 工数の新規登録・編集・削除で関連キャッシュを即時無効化し、次回読み込みは更新後の正本から行う。
- 期間外への移動で未取得の場合は選択日を即時に更新し、ローディング表示と取得失敗時の再試行導線を提供する。
- 本番環境の実通信時間はブラウザとApps Scriptの実測により評価し、キャッシュ内遷移が通信ゼロであることを自動テストで保証する。

### 3.10 工数入力の安全な日付移動 v0.11.2

- 日付の前日/翌日ボタンに説明ラベルを付け、日付入力欄で離れた日にも直接移動できるようにする。選択済み14日キャッシュは従来どおり再利用する。
- 未保存のクイック入力（案件、分類、開始、終了、作業内容）は、日付切替・非同期再描画・メニュー移動で消えないよう、そのブラウザ内で日付別に一時保持する。保持はセッションと社員に結び付け、最大20日分とする。
- 一時保持データはサーバーに送らず、ログアウト時に消去する。正常に登録できた日付の一時入力は破棄し、保存に失敗した場合は保持する。
- 登録ボタンの連続クリックによる二重送信を防止する。開始時刻より後の終了時刻だけを受け付ける。
- 日付移動や再読み込み後も入力欄・日付操作のフォーカスを可能な限り維持し、キーボードとスマートフォンで操作可能にする。
- 過去日を表示する際は「本日」と誤解させない表示見出しを使用する。


### 3.11 全画面共通のUI/UX統一とホーム初期画面 v0.12.0

**範囲:** ホーム・勤怠・工数・予定表・申請・管理・事務・ログイン・各種モーダル・PCとモバイルメニュー。

- `Styles.html` 末尾に一元管理の **FM WORKS Design System v1** を配置し、共通のフォント・文字サイズ・青/補助文字色・ボタン高さ・角丸・カード・フォーム・フォーカス表示を統一する。新ページのCSSは共通トークンを再利用し、局所的な強制上書きを避ける。
- 通常文字の色は背景に対して約4.5:1以上、押しやすい操作領域を確保。ライトの補助色 `#60728a`、主要青 `#0969da`、ダークの補助色 `#aebcd0` と主要青 `#4d9aff` を使い、色だけに頼らず状態名を表示する。
- FMロゴは SVG `fill=currentColor` のまま `--ui-brand-ink` で制御し、ライトは `#111c23`、ダークは `#f5f9ff`。PCサイドバー、モバイルヘッダー、モバイルドロワー、ログインにも適用する。
- ホームは標準100%・主要PC画面（1366x768、1790x850、1920x1080）で主要な「4指標・打刻・要対応・予定・ショートカット」を原則1画面内に収める。余白・カード・上段ヘッダーを圧縮するが、**文字サイズ拡大・ズーム・多件数時はスクロール可能としコンテンツを切り捨てない**。スマホの読み順は変えない。
- 画面共通部品と詳細は `docs/UI_DESIGN_SYSTEM.md` に定義する。以後のUI改修はこのルールと既存の画面品質テストを必須とする。
- 画面内容により最適密度は異なるため、工数タイムラインや月・週・日の予定グリッドの機能的な密度まで一律には強制しない。

**受入条件:** 全画面の共通表示、ロゴ色のライト/ダーク切替、ホーム短縮レイアウトの安全なCSS条件、フォント拡大時の可読性、権限・操作・既存CIの回帰を確認する。

## 4. ライト / ダークテーマ

- ライト、ダークの2テーマを提供する。
- 初回はOSの `prefers-color-scheme` を参照する。
- 以後はユーザーが選んだテーマを `localStorage` に保存する。
- 切替時は約0.5〜0.7秒かけて色・背景・グラデーションが滑らかに移行する。
- 対応ブラウザではView Transition APIを利用し、非対応ブラウザはCSSトランジションへフォールバックする。
- `prefers-reduced-motion: reduce` の場合は大きな演出を抑制する。

## 5. 認証

### 5.1 ログイン

- 社員ID + 6桁PIN。
- 試作モードでは架空社員 `FM0001〜FM0005` のみ共通PIN `000000` を許可できる。
- 本番モードでは社員ごとのPINのみ。
- 「この端末でログイン状態を保持する」をONにした場合は最大30日保持する。

### 5.2 PIN保護

- PIN平文保存禁止。
- 社員別Salt + Script Properties上のPepper。
- HMAC-SHA256でハッシュ化。
- 失敗回数制限と一時ロック。
- 仮PINは初回変更必須。

### 5.3 セッション

- ブラウザには生トークン。
- DBにはトークンハッシュのみ。
- absolute expiry / idle expiryを持つ。
- ログアウト、PIN変更、社員無効化、試作モード終了時に失効する。

## 6. 勤怠

- 勤務中の「現在の実働」は初回取得値で止めず、サーバー時刻を基準にブラウザ上で継続更新する。
- 休憩中・退勤済みは実働時間を増加させない。
- 打刻直後はサーバーから返る時刻を新しい基準時刻として採用する。


### 6.1 打刻種別

1. 出勤
2. 休憩開始
3. 休憩終了
4. 退勤

勤務場所は `出社 / 在宅 / 外出`。

### 6.2 打刻順序

サーバー側で順序検証を行う。

- 退勤前に出勤が必要。
- 休憩終了前に休憩開始が必要。
- 重複出勤など不正遷移を拒否する。

### 6.3 打刻修正

- 元打刻を物理更新・削除しない。
- 修正レコードを追加する。
- 元打刻IDとの関係を残す。
- 承認操作と監査ログを必須とする。

### 6.4 休憩チェック

- 実働6時間超: 45分以上。
- 実働8時間超: 60分以上。
- 不足は月次の要確認理由にする。

## 10.2 操作遅延・視認性の根本改善 v0.11.4

- 同一月の「月・週・日・一覧」の切替と社員・分類フィルター変更では、**サーバーへの再問い合わせを行わない**。初回取得時は選択月の月間表示に必要な全日付・全社員・全分類の予定を1回で読み込む。
- クライアントはサーバー側の公開範囲・閲覧権限が適用済みの予定だけを保持する。社員・分類の絞り込みは認可済みデータの範囲内で実施し、非公開予定を追加取得しない。
- 一時的な通信失敗時も表示済みの予定は残し、30秒間は自動再試行を抑制して通信を連発しない。手動の再読込は引き続き可能にする。
- 土曜日の休日ラベルは青系、日曜・祝日・会社休日のラベルは赤系に統一する。
- 読み込み済みの別月へ戻る際も、使用中ブラウザの一時キャッシュを再利用する。最大6期間、3分以内は再通信しない。期限切れでも古い内容を先に表示し、バックグラウンドで再取得する。更新中の目印を表示する。
- 未取得の月は通信が必要なため「瞬時」を保証しない。日付変更の連打では同一要求をまとめ、並列読込は最大2件に制限する。
- 保存・削除・会社カレンダー更新・ログアウト時は予定のキャッシュを破棄し、古い通信結果を取り込まない。社員が変わった後の予定が混じらないよう利用セッションごとに分離する。
- 予定表の画面説明でも社員名がカードに表示されることを明記する。
- 強調表示によって、週・日表示の予定カードの時間位置や重複配置が変わらないこと。
- 社員名の色付きチップはボタンとして操作できる。押した社員の参加予定（共同参加を含む）を強調し、それ以外を薄くする。再クリックまたは「解除」で通常表示へ戻す。ハイライトは予定を隠さず、社員絞り込みとは別に機能する。
- 月カレンダーの日付区切りを太く明確にし、日曜・祝日・会社休日は赤系、土曜は青系、調整出勤は緑系で示す。ダークモードでも同等の視認性を維持し、色だけでなく曜日・休日名も表示する。
- 既存の予定登録・編集・閲覧制限・週・日・一覧・会社カレンダーの導線を残す。

**完了条件:** 読込済みの同一月で月/週/日/一覧/社員/分類/社員ハイライトの操作を連続実行しても `getScheduleBundle` 呼び出しが0回。新しい月は1回。再訪時は0回。保存後の再読込と別社員のアクセス遮断が検証できること。

### 12.1 申請ダッシュボードの再設計 v0.11.5

目的：社員が迷わず素早く申請し、申請後の状態を確認できる。管理者は承認待ちと取消確認を見逃さない。

- **状況の見える化**：申請状況の上部指標はクリック可能。一般社員は「承認待ち／差戻し／承認済／申請可能な有給」、承認権限者は「チームの要対応／自分の承認待ち／自分の差戻し／申請可能な有給」を優先表示する。
- **残有給の正確性**：取得した本人の有給台帳情報だけ表示する。未設定の場合はコンパクトな案内と、権限者向けの社員設定導線を表示する。未設定の残数・承認数に架空値を入れない。
- **クイック申請**：有給、半休・1/4日、打刻修正、在宅勤務、残業、休日出勤、欠勤の既存入力導線を保持。申請ボタンを選ぶと直接入力モーダルを表示し、申請完了まで不要な確認ページを挟まない。
- **ガイド切替の性能**：半休の区分変更時に日数確認APIを重複実行しない。更新後の値をセットしてから1回だけ確認する。
- **入力ガイド**：モーダル内に「①種類選択→②日付と理由→③内容確認」の短いガイドを表示。入力中の種別・対象日・理由を通信なしでプレビューする。半休区分切替時は日付、理由、補足を保持する。
- **役割に応じた表示**：承認権限がある場合のみ部下の承認待ちと承認済み取消確認の一覧・操作を表示。一般社員には直近の自分の申請とガイドを表示する。自身の申請は承認対象に混ぜない。
- **大量申請への対応**：チーム承認待ちは初期4件、追加表示で8件ずつ開き、100件を超えても続けて表示できる。追加表示によるサーバー通信は発生させない。
- **申請履歴**：すべて／承認待ち／承認済／差戻し／取消関連を取得済みデータで瞬時に切替。理由・日付・種別の検索、10件ごとの追加表示、詳細確認を提供する。操作ごとに追加のGAS通信を発生させない。
- **安全性**：申請の承認/取消/承認済み取消依頼の既存APIとサーバー権限判定を変更しない。申請ID・理由等は表示前にエスケープし、データを別ユーザーへ漏らさない。ログアウト/再ログイン時は一覧・キャッシュを消去し、古い通信応答を破棄する。
- **誤操作防止**：申請の連打による二重送信を防ぐ。失敗した場合は入力内容を保持して再申請できるようにする。モーダルの保存ボタンを送信中に無効化する。
- **見た目と機器対応**：PCは状況指標4列、クイック申請＋対応パネル、その下に履歴。スマホ・タブレットでは積み重ね、クリック領域を確保する。ライト/ダーク切替に対応し、色だけで承認状態を示さない。
- **データの真実性**：ステータス数値は `getRequestsBundle` の本人と担当者向けの認可済みレスポンスから計算し、「当月件数」のような裏付けのない数値を表示しない。

受入検証：一般社員/承認権限者で表示差異、取消確認対応、履歴切替/検索/追加表示はGAS通信0回、申請フォームの既存送信契約、二重送信防止、他セッションの応答破棄、XSS対策、PC・タブレット・スマートフォンでの横はみ出しゼロ、CI全試験成功。

### 13.1 入社日からの年休自動管理と年5日通知（v0.11.7）

- 自動付与の日付計算には存在する入社日および判定基準日（YYYY-MM-DD）のみを使用する。2月31日や13月など不正な日付から付与日・有給残数を生成せず、付与計画を無効として処理を保留する。月末・うるう年における正しい6か月後の計算は維持する。

- 入社6か月後から10、11、12、14、16、18、20日の法定年休を毎年計算し、6年6か月以降は毎年20日を上限とする。
- 管理者が入社日を登録し、一般労働者相当の勤務契約を確認して社員ごとの自動付与を有効にする。短時間労働者の比例付与は個別管理とする。
- 付与前の期間について会社カレンダー、打刻、承認済み年休による出勤率80％以上の確認を必須とし、証拠不足なら付与を保留して管理者確認を促す。アプリに記録されていない産休・育休などのみなし出勤は自動推定しない。
- 自動管理の有効化後に年をまたいで未処理となった付与日を一覧化し、過年度分は重複付与・失効の問題があるため管理者確認とする。新年度の付与で未処理の注意を消さない。
- 台帳の自動付与GRANT記録が成功したのに社員マスタ残数の反映に失敗した場合は、次回の判定時に台帳の最新残数と基準日へ安全に再同期する。新たなGRANTは重複作成しない。
- 自動付与は年休台帳のGRANT、社員マスタ残数・基準日、監査ログの3つへ反映し、同一付与日の二重記録を防止する。設定有効化前の過去年数分は自動付与しない。既存社員の初期残数・付与記録を保護する。
- 日次付与チェックは管理者が一度設定するApps Scriptトリガーで実行し、アプリ起動・申請・通知時にも未反映分を確認する。トリガー未設置でもアクセス時に付与判定を行う。
- 有給申請は承認待ちの仮引き、承認済みの確定減算、取消承認による残数戻しを既存台帳で処理。古い社員編集画面から残数が上書きされないよう更新競合を検知する。
- 前年度の年5日取得が未達だった場合は、翌年の新規付与によって注意が消えないよう前年度分も確認表示する。
- 年5日の判定に必要な会社カレンダーや付与記録が不足する場合は、誤って達成・未達と断定せず社員への確認通知を表示する。
- 年10日以上付与された人には年5日の取得状況を通知。期限180日前から不足を目立たせ、期限超過も警告する。全日・半日の取得をカウントし、1/4日有給は法的区分未確定のため算入しない。未承認と未来の休暇は実績に含めない。
- 申請画面に取得済み・残り日数・期限・達成を表示。管理者は年休台帳・社員詳細で付与状態、次回付与、処理保留理由を確認できる。
- 既存付与ロットの失効日は未整備なため、2年の自動失効は今回行わず、従来の年休台帳の失効操作を維持する。履歴の確認なく残数を消去しない。

受入条件：6か月／1年6か月／6年6か月後の計算、79％／80％の条件判定、既存残数保護、同日二重付与防止、申請時の仮引き、承認・取消の確定、年5日の通知、権限とログイン分離、全既存CI試験に合格する。


### 13.2 有給休暇のダミーデータ・操作デモ（v0.11.8）

目的：実在社員や年休台帳を変更せず、入社日→付与日→申請→承認→取消→年5日の進み具合を実際に操作して理解できること。

- 「管理 → 社員・権限」「申請」の両方に、架空の社員による有給操作デモの入口を設ける。ログインしている場合のみ利用できる。
- 基準日2026-10-08で、初回10日、2年目11日と繰越、長期勤続20日と5日達成、取得期限間近の4人の架空社員・架空取得履歴を用意。実在社員の名前、社員番号、申請内容は用いない。

## 22. 承認階層と職務分掌

社員権限に `MANAGER` を追加する。

- USER: 自分の勤怠・工数・予定・申請
- CALENDAR_EDITOR: USER + 会社カレンダー編集
- MANAGER: USER + 直属部下の申請承認 + 直属部下の月次閲覧
- ADMIN: 全体管理。ただし自分自身の申請は承認不可

社員マスタX列 `直属承認者ID` を使用する。

承認条件:

1. 申請者と承認者が同一人物なら必ず拒否する。
2. MANAGERは `直属承認者ID === 自分の社員ID` の社員だけ承認できる。
3. ADMINは他社員を承認できるが、自分自身は承認できない。
4. 権限判定はサーバーAPIで再検証する。
5. MANAGERの月次社員選択肢は自分 + 直属部下だけ。
6. 月次締め・一括給与出力・社員設定はADMINのみ。

### 22.1 追加受入条件

- 自己承認APIは失敗する。
- MANAGERが非直属社員を承認しようとすると失敗する。
- MANAGERがURL/APIから非直属社員の月次を指定しても失敗する。
- MANAGER画面には月次締めと給与一括出力を表示しない。


## 23. 月次締め確定スナップショット

月次締めは単なる `CLOSED` フラグではなく、締め時点の給与対象社員の月次・日次値を確定スナップショットとして保存する。

- `月次確定`: 社員別月次合計、締め日時、締め者、SHA-256データハッシュ
- `月次確定日次`: 日付ごとの出退勤、実働、残業、休日勤務、遅刻早退、休憩、工数、勤務場所、休暇、要確認
- `月次締め`: 使用したスナップショットIDを保持
- 締め済み月の個人Excelは確定スナップショットから作成
- 給与対象一括Excelは月次締め後のみ作成可能で、確定スナップショットを使用
- 締め解除後の再締めは新しいスナップショットIDを発行し、過去スナップショットは削除しない

これにより「同じ締めIDなら同じ給与根拠値」を再現できること。


## 24. 有給台帳と承認済み取消

有給残日数は社員マスタの単一数値だけで管理しない。社員ごとに有給台帳を保持する。

有給台帳は少なくとも以下を保持する。

- 年休基準日
- 取引日
- 種別: OPENING / GRANT / USE / RESTORE / EXPIRE / ADJUST
- 増減日数
- 取引後残日数
- 関連申請ID
- 処理者
- 処理日時
- 備考

社員設定で有給残を初めて設定する場合、年休基準日を必須とする。以後の管理者による残数変更はADJUSTとして履歴化する。

有給承認はUSE、承認済み有給の取消承認はRESTOREを記録し、社員マスタの有給残は表示用キャッシュとして同期する。

承認済み申請は本人が取消理由を入力して「取消申請中」にできる。元の承認者権限範囲にある別人が取消承認/取消却下を行う。承認済み打刻修正は直接巻き戻さず、新しい打刻修正申請で訂正する。

管理画面の社員一覧から「年休」を開き、GRANT / EXPIRE / ADJUSTを台帳へ登録できる。GRANTで10日以上の新規付与記録がある社員について、基準となる付与日から1年間の年5日取得状況を監視する。全日有給と午前/午後半休を取得実績へ算入し、会社規程上の法的区分が未確定の1/4日有給は年5日実績へ自動算入しない。

付与記録がない、または会社カレンダーが不足する場合は「判定材料不足」とし、法令対応済みとは表示しない。年5日未達で期限120日以内または期限超過の場合は通知する。

年休管理簿の保存期間や個別の付与方式・基準日統一/分割付与等は会社運用を確認し、システムの自動判定だけを専門家判断の代替にしない。

## 26. 実行環境とDB分離

実行環境は `DEVELOPMENT / STAGING / PRODUCTION` のいずれかとする。

- Script Property `FM_WORKS_ENVIRONMENT` 未設定時はSTAGING。
- DEVELOPMENT/STAGINGは既定DBへフォールバック可能。
- PRODUCTIONは `FM_WORKS_DB_ID` の明示設定を必須とする。
- PRODUCTIONでSTAGING既定DBを再利用することは禁止する。
- システム状態に現在の実行環境を表示する。
- 本番運用チェックはPRODUCTION以外を未完了として扱う。
- 試作PIN終了と実行環境昇格は別工程とし、誤って本番設定へ切り替わらないようにする。


## 27. 自動バックアップ時間トリガー

DBバックアップは管理者のログイン有無に依存させない。

- 毎日03時台にApps Script時間トリガーから実行する。
- 同じ日に既に成功していればスキップする。
- Script Lockで重複実行を防止する。
- 有効化時は時間トリガーを1件だけ作成する。
- 無効化時は対象トリガーを削除する。
- 管理画面からトリガーを再設定できる。
- 成功/失敗を監査ログへ記録する。
- 保持期間は90日。
- コピー後に全シートの存在・最終行・最終列を原本と照合し、整合性確認に成功したコピーだけを「成功バックアップ」と記録する。
- 整合性未確認の最新バックアップがある状態では本番READYにしない。


## 28. 労務計算モデル v0.9.6

## 35. 36協定の年次・複数月監視 v0.10.3

日本・一般則プロファイルを「設定済み」とするには、週開始曜日に加えて次を必須とする。

- 36協定の対象期間の起算月（1〜12月）
- 特別条項の有無（なし / あり。未確認は不可）

一般則の監視値は厚生労働省が示す基準を基礎とする。

- 時間外＋法定休日: 2〜6か月平均80時間以内
- 月45時間を超えられる月数: 年6か月まで

これらは一般則の監視支援であり、変形労働時間制、フレックスタイム制、業種別特例、個別36協定の具体的上限を自動的に法令適合判定しない。

## v0.17.4 書類履歴の切替速度と誤表示防止（2026-10-10）

- 書類履歴で別の書類を素早く選んだ場合、後から返ってきた古い詳細取得結果や通信エラーは、現在選択中の書類を上書きしない。
- 同一書類の詳細を重複して要求しない。更新日時が変わっていない書類は、同一ログイン中に読み込んだ最大12件の詳細をブラウザ内メモリから再表示し、不要なGAS通信を削減する。
- 更新日時が変わった書類・通信失敗後の再試行では実データを再取得する。ログインユーザーが変わったら前ユーザーの詳細キャッシュを引き継がない。キャッシュはブラウザ内メモリだけで、WebStorage・実DB・保存ファイルは変更しない。
- 書類の参照権限はサーバー側で毎回検査される既存仕様を維持し、正式発行済みの明細・金額・PDF/Excel・元見積に変更を加えない。
