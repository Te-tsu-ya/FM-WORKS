# FM WORKS 要件定義書

**文書版:** 0.11.0  
**更新日:** 2026-10-08  
**正本:** GitHub `docs/REQUIREMENTS.md`

## 1. 目的

FM WORKSは、社員の勤怠、工数、予定、申請、会社カレンダー、月次確認、管理を一つのWebアプリに統合する社内向けワークポータルである。

本書は、別のエンジニアが本書と技術設計書だけを読み、同等機能を再実装できる粒度で機能要件・業務ルール・画面要件・非機能要件を定義する。

## 2. 対象ユーザーと権限

| ロール | 主な権限 |
| --- | --- |
| USER | 自分の勤怠、工数、申請、月次確認。共有予定表・会社カレンダー閲覧 |
| CALENDAR_EDITOR | USER権限 + 会社カレンダー編集 |
| MANAGER | USER権限 + 直属部下の申請承認・月次閲覧 |
| ADMIN | 全機能。社員・認証・他社員承認・プロジェクト・運用設定・設計文書閲覧 |

管理系APIは画面制御だけに依存せず、Apps Script側で必ず再認証・再認可する。

## 3. 画面構成

### 3.1 共通ナビゲーション

左サイドバーのトップ階層は日常業務へ絞り、以下を表示する。

- ホーム
- 勤怠
- 工数
- 予定表
- 申請
- 管理（ADMINのみ）

トップ階層から外した機能は削除せず、関連ワークスペースへ統合する。

- 勤怠: 本日 / 月間 / 履歴
- 予定表: 予定 / 会社カレンダー
- 管理: 社員・権限 / 認証・サポート / プロジェクト / 運用・労務 / 要件定義書 / 技術設計書

月次、会社カレンダー、社員管理の旧内部ルートは既存リンク互換のため維持し、左ナビ上では親メニューをアクティブ表示する。

### 3.2 1画面完結方針

- PCで1ビューポート完結を優先するのはホーム、勤怠「本日」、工数「本日」とする。
- 月次・設定・年間カレンダーは可読性を優先し、ページ全体を自然にスクロールさせる。
- 情報量が多い表・文書はページ全体ではなくパネル内スクロールを使う。
- スクロールしなければ主要操作に到達できない構造を減らす。
- モバイルは画面幅の制約を優先し、必要な場合のみ縦スクロールを許容する。

### 3.3 クリック視認性

- ボタン、カード、日付セル、セレクト、ナビ、クリック可能行はポインタカーソルを表示する。
- 独立したポインタ操作対象は原則24×24 CSS px以上を確保し、小型ボタンは28px以上を基本とする。
- ホバー時に背景・枠・影のいずれかが変化する。
- キーボード操作時は `:focus-visible` を明確に表示する。
- 色だけで状態を伝えず、文言・アイコン・バッジを併用する。

### 3.4 ホーム

PCのホームは縦積みカードではなく、1画面の業務ダッシュボードとして構成する。

上段「コマンドバー」:

- 挨拶
- 当日の日付
- 会社カレンダー区分
- 今月の勤務時間
- 今月の残業
- 有給残

下段は3カラム:

1. **現在の勤怠**
   - 勤務状態
   - 出勤 / 実働 / 退勤
   - 出勤・休憩・退勤操作
   - 勤務場所
   - 当日の打刻履歴
2. **今日の予定**
   - 時刻
   - 件名
   - 参加者名
   - 場所
   - 詳細な予定表への導線
3. **やること**
   - 工数
   - 勤怠確認
   - 申請/承認
   - 工数・申請・月次へのクイック導線

PCではページ全体を縦スクロールさせず、件数が多い予定・打刻履歴だけカード内部でスクロールする。

高さ760px以下の広いPCでは余白・フォント・パネル内間隔を圧縮する。画面幅1140px以下では3カラムを無理に詰めず、ホームだけ1画面固定を解除して1カラムの通常スクロールへ切り替える。

### 3.5 勤怠ワークスペース

勤怠は「本日 / 月間 / 履歴」の3タブで構成する。

**本日**は、最初の3〜5秒で「現在の状態」「次に行う打刻」「確認が必要な問題」が分かることを最優先する。

上段:
1. 現在の勤務状況
   - 勤務中 / 休憩中 / 退勤済み / 勤務外
   - 実働時間
   - 出勤・休憩・退勤操作
   - 勤務場所
2. 今日の勤務タイムライン
   - 出勤、休憩開始、休憩終了、退勤
   - 現在状態
   - 会社カレンダーに終了時刻がある場合は退勤予定
3. 確認が必要なこと / 本日の集計
   - 月次本人確認
   - 打刻問題
   - 工数差異
   - 実働、休憩、予定勤務に対する残り時間

下段:
- 当月の簡易カレンダー
- 今月の出勤日数、実働、残業、有給取得
- 直近5日程度の勤怠履歴

当月カレンダー・月間サマリー・履歴は初期打刻UIをブロックしてはならない。`getMonthlySummary` は本日画面描画後に遅延取得し、取得中も出退勤・休憩・勤務場所の操作を可能とする。

「保存先 Google Sheets」等の技術実装情報は一般社員の勤怠画面へ主要情報として表示しない。

### 3.6 勤怠本日の1画面表示と検証用サンプル

- PC幅1141px以上では、勤怠「本日」の主要領域をページスクロールなしで1画面に収める。
- 高さが低いPCでは余白・カード内パディング・タイムライン間隔を縮め、主要操作と月間プレビューを同一画面内に維持する。
- 幅1140px以下は可読性を優先し、通常の縦スクロールへ戻す。
- 実データがまだ無いADMINには、カレンダー・月間集計・直近履歴・警告状態を評価できる表示確認用サンプルをクライアント側だけで生成する。
- サンプルには正常勤務、在宅、工数差異、有給、打刻不足を含める。
- サンプルは「表示確認用サンプル」と明示し、Google SheetsやサーバーAPIへ書き込まない。
- サンプル日をクリックした場合は読み取り専用の詳細モーダルを表示し、申請・締め・Excel出力等の実データ操作へ混入させない。
### 3.7 可読性と勤務途中の勤務場所変更

#### 可読性
- 勤怠「本日」は1画面性を維持しつつ、通常利用者が読む本文・表・カレンダー・状態ラベルをv0.10.8より一段大きくする。
- 装飾目的の英字eyebrow等は情報本文より優先しない。
- トップバーに「文字サイズ：標準 / 大きめ」の切替を置き、選択を `localStorage['fmworks.fontSize']` に保存する。
- 「大きめ」では可読性を1画面固定より優先し、必要なら勤怠ページの縦スクロールを許可する。

#### 勤務場所の途中変更
- 勤務場所は `出社 / 在宅 / 外出`。
- 出勤前は勤務場所ボタンを「次の出勤打刻で使用する場所」の選択として扱う。
- 勤務中または休憩中に別の勤務場所を選択した場合、単なる表示切替ではなく「勤務場所変更」として時刻付きで打刻ログへ追記する。
- 例: `09:00 出勤（出社） → 13:30 勤務場所変更（出社→在宅） → 18:00 退勤（在宅）`。
- 勤務場所変更は実働時間・休憩時間の計算状態を変化させない。
- 退勤後の勤務場所変更は拒否する。
- 当日のタイムラインに勤務場所変更を表示する。
- 月次の日別「勤務場所」は1日の遷移を `出社→在宅` のように要約表示し、その日のどこかで在宅勤務を含めば在宅勤務日として集計する。
- 打刻修正申請の対象は従来どおり出勤・休憩開始・休憩終了・退勤とし、「勤務場所変更」を打刻時刻修正の種別へ混入させない。
- 勤務場所変更は監査ログに変更前・変更後を記録する。

### 3.8 工数ワークスペース v0.11.0

工数「本日」は、**勤怠時間に対して未入力の時間を見つけ、その場で埋める**ことを最優先する。

PC上段:
- 入力済工数
- 本日の実働
- 未入力時間
- プロジェクト数

PC中段:
1. **本日のタイムライン**
   - 工数登録済み区間をプロジェクトごとに色分け
   - 勤怠の休憩履歴がある区間は「休憩」
   - 勤怠時間内で工数が無い区間は「未入力」
   - 未入力区間をクリックすると、右側クイック入力の開始・終了へ時刻を転記
2. **クイック入力**
   - プロジェクト
   - 作業分類
   - 開始 / 終了
   - 作業内容
   - 「登録する」で既存 `saveWorklog` APIへ保存
   - 詳細な備考や既存データ編集は従来の工数モーダルを使用

PC下段:
- 本日の工数一覧
- 時間 / プロジェクト / 作業分類 / 内容 / 工数 / 状態 / 操作
- 件数が多い場合はページ全体ではなく一覧パネル内部だけをスクロール

PC幅1141px以上では、主要KPI・タイムライン・クイック入力・工数一覧を1ビューポートへ収めることを優先する。幅1140px以下ではタイムラインとクイック入力を縦積みにして通常スクロールへ戻す。

当日の実働時間は勤怠データと連携する。工数登録済み時間との差を未入力時間として表示する。現在勤務中の場合は、サーバー基準時刻から経過分を加算した実働時間を利用する。

ADMINで当日の工数実データが0件の場合、デザイン確認用としてブラウザ内だけのサンプルを表示してよい。サンプルは「表示確認用サンプル」と明示し、Google Sheetsへ保存しない。サンプルは複数プロジェクト、休憩、未入力時間を含める。実プロジェクトが無い場合、クイック入力の保存は無効化する。 サンプルのプロジェクト名は実在顧客・実案件を使わず匿名名称とする。

## 4. ライト / ダークテーマ

- ライト、ダークの2テーマを提供する。
- 初回はOSの `prefers-color-scheme` を参照する。
- 以後はユーザーが選んだテーマを `localStorage` に保存する。
- 切替時は約0.5〜0.7秒かけて色・背景・グラデーションが滑らかに移行する。
- 対応ブラウザではView Transition APIを利用し、非対応ブラウザはCSSトランジションへフォールバックする。
- `prefers-reduced-motion: reduce` の場合は大きな演出を抑制する。

## 5. 認証

### 5.1 ログイン

- 社員ID + 6桁PIN。
- 試作モードでは架空社員 `FM0001〜FM0005` のみ共通PIN `000000` を許可できる。
- 本番モードでは社員ごとのPINのみ。
- 「この端末でログイン状態を保持する」をONにした場合は最大30日保持する。

### 5.2 PIN保護

- PIN平文保存禁止。
- 社員別Salt + Script Properties上のPepper。
- HMAC-SHA256でハッシュ化。
- 失敗回数制限と一時ロック。
- 仮PINは初回変更必須。

### 5.3 セッション

- ブラウザには生トークン。
- DBにはトークンハッシュのみ。
- absolute expiry / idle expiryを持つ。
- ログアウト、PIN変更、社員無効化、試作モード終了時に失効する。

## 6. 勤怠

- 勤務中の「現在の実働」は初回取得値で止めず、サーバー時刻を基準にブラウザ上で継続更新する。
- 休憩中・退勤済みは実働時間を増加させない。
- 打刻直後はサーバーから返る時刻を新しい基準時刻として採用する。


### 6.1 打刻種別

1. 出勤
2. 休憩開始
3. 休憩終了
4. 退勤

勤務場所は `出社 / 在宅 / 外出`。

### 6.2 打刻順序

サーバー側で順序検証を行う。

- 退勤前に出勤が必要。
- 休憩終了前に休憩開始が必要。
- 重複出勤など不正遷移を拒否する。

### 6.3 打刻修正

- 元打刻を物理更新・削除しない。
- 修正レコードを追加する。
- 元打刻IDとの関係を残す。
- 承認操作と監査ログを必須とする。

### 6.4 休憩チェック

- 実働6時間超: 45分以上。
- 実働8時間超: 60分以上。
- 不足は月次の要確認理由にする。

## 7. 月初の先月勤怠確認

### 7.1 自動アラート

- 毎月1日以降、前月の本人確認が完了していない社員へアラートを出す。
- アラートはホームだけでなく全画面上部に表示する。
- 通知メニューにも「勤怠確認」を出す。
- 確認完了するまで継続表示する。
- 月が変わっても未確認月を消さず、`MONTHLY_REVIEW_START_MONTH` 以降の未確認・再確認月を古い順に案内する。
- 1つの月を確認完了した後、未確認月が残っていれば次の対象月を自動表示する。
- `MONTHLY_REVIEW_DUE_DAY` の既定値は5日。
- 1日〜期限日はwarning。
- 期限超過後はdanger。

### 7.2 再確認

確認後に対象月の以下が更新された場合は、確認済みを再確認状態として扱う。月をまたいでも再確認義務を失わない。

- 打刻
- 工数
- 申請
- 会社カレンダー

### 7.3 確認完了条件

本人が自分の過去月を確認する。

確認完了ボタンは以下が0件の場合だけ有効。

- 要確認日
- 工数差異日

ADMINが月次画面で他社員を選択した場合、その社員の本人確認状態を読み取り専用で表示する。ADMINが本人確認を代理完了することはできない。

確認時に以下を記録する。

- 年月
- 社員ID
- 氏名
- 状態
- 確認日時
- 確認者
- 確認時最終更新
- メモ
- 登録日時
- 更新日時

## 9. 工数

- 進行中プロジェクトから選択。
- 作業内容必須。
- 開始・終了必須。
- 同一社員・同一日の重複時間帯禁止。
- 削除はソフトデリート。
- 月次締め済み月は追加・編集・削除禁止。
- 実働との差が5分超の場合は月次で工数差異。

## 10. 予定表

- 月 / 週 / 日 / 一覧。
- 予定カードに社員名を直接表示。
- 社員色は補助情報。
- カテゴリ色とは分離。
- 複数人は先頭2名 + 残人数。
- 色だけで担当者を判断させない。

## 11. 会社カレンダー

- 登録済み年度だけ表示。
- 未作成年度は自動表示しない。
- 権限者が「YYYY年を作成」を押した時点で生成。
- 初期生成は土日・国民の祝日。
- 会社独自休日・年末年始・調整出勤日は人が確認して修正。

## 12. 申請

申請種別:

- 有給
- 午前半休
- 午後半休
- 1/4日有給
- 欠勤
- 打刻修正
- 在宅勤務
- 残業
- 休日出勤

画面要件:

- 「何を申請しますか？」のクイックカード。
- 選択後は必要項目だけ表示。
- 有給系は現在残 / 承認待ち / 申請可能残 / 今回消化 / 申請後残数。
- エラーはフォーム内に具体的に表示。
- エラー項目へフォーカス。
- Toastは補助に留める。

## 13. 有給

- 有給残日数は0.25日単位。
- 実値不明なら仮値を設定しない。
- 未設定は明示。
- 承認待ち分を申請可能残から差し引く。
- 不足する申請は申請前に拒否する。

## 14. 月次締め

ADMINのみ。

締め前条件:

- 給与対象者1名以上。
- 要確認勤怠0。
- 工数差異0。
- 承認待ち申請0。

締め後:

- 工数追加・編集・削除停止。
- 対象月の申請承認停止。

解除:

- ADMINのみ。
- 理由必須。
- 監査ログ必須。

## 16. 管理

ADMINの管理画面をタブ化する。

- 認証・サポート
- プロジェクト
- 運用設定
- 要件定義書
- 技術設計書

プロジェクトタブでは、既存プロジェクトの一覧・編集と新規追加を行えること。設定画面の再構成によってこの機能を失わないこと。

### 16.1 要件定義書・技術設計書

- ADMINのみ閲覧可能。
- GitHub Markdownを正本とする。
- デプロイ時にApps Script用データへ生成。
- アプリ内で見出し、表、リスト、コードを読みやすく表示。
- 「再読込」はクライアントキャッシュを無視し、現在のデプロイ文書を再取得する。

## 17. 文書同期ルール

- `src/**` の変更を伴うコミットは、同じコミットで `docs/REQUIREMENTS.md` と `docs/TECHNICAL_DESIGN.md` の両方を更新する。
- GitHub Actionsで検査する。
- 片方でも未更新ならデプロイ失敗。
- 文書版と `APP.version` を一致させる。
- UI変更、業務ルール、データ構造、API、セキュリティ、運用変更はすべて文書反映対象。

## 18. 性能

- ログイン直後は「認証・本日の勤怠・今日の予定・会社カレンダー当日・社員/プロジェクトマスタ」を先に返し、月次集計・申請件数・月次本人確認はホーム概要として非同期取得する。

## 22. 承認階層と職務分掌

社員権限に `MANAGER` を追加する。

- USER: 自分の勤怠・工数・予定・申請
- CALENDAR_EDITOR: USER + 会社カレンダー編集
- MANAGER: USER + 直属部下の申請承認 + 直属部下の月次閲覧
- ADMIN: 全体管理。ただし自分自身の申請は承認不可

社員マスタX列 `直属承認者ID` を使用する。

承認条件:

1. 申請者と承認者が同一人物なら必ず拒否する。
2. MANAGERは `直属承認者ID === 自分の社員ID` の社員だけ承認できる。
3. ADMINは他社員を承認できるが、自分自身は承認できない。
4. 権限判定はサーバーAPIで再検証する。
5. MANAGERの月次社員選択肢は自分 + 直属部下だけ。
6. 月次締め・一括給与出力・社員設定はADMINのみ。

### 22.1 追加受入条件

- 自己承認APIは失敗する。
- MANAGERが非直属社員を承認しようとすると失敗する。
- MANAGERがURL/APIから非直属社員の月次を指定しても失敗する。
- MANAGER画面には月次締めと給与一括出力を表示しない。


## 23. 月次締め確定スナップショット

月次締めは単なる `CLOSED` フラグではなく、締め時点の給与対象社員の月次・日次値を確定スナップショットとして保存する。

- `月次確定`: 社員別月次合計、締め日時、締め者、SHA-256データハッシュ
- `月次確定日次`: 日付ごとの出退勤、実働、残業、休日勤務、遅刻早退、休憩、工数、勤務場所、休暇、要確認
- `月次締め`: 使用したスナップショットIDを保持
- 締め済み月の個人Excelは確定スナップショットから作成
- 給与対象一括Excelは月次締め後のみ作成可能で、確定スナップショットを使用
- 締め解除後の再締めは新しいスナップショットIDを発行し、過去スナップショットは削除しない

これにより「同じ締めIDなら同じ給与根拠値」を再現できること。


## 24. 有給台帳と承認済み取消

有給残日数は社員マスタの単一数値だけで管理しない。社員ごとに有給台帳を保持する。

有給台帳は少なくとも以下を保持する。

- 年休基準日
- 取引日
- 種別: OPENING / GRANT / USE / RESTORE / EXPIRE / ADJUST
- 増減日数
- 取引後残日数
- 関連申請ID
- 処理者
- 処理日時
- 備考

社員設定で有給残を初めて設定する場合、年休基準日を必須とする。以後の管理者による残数変更はADJUSTとして履歴化する。

有給承認はUSE、承認済み有給の取消承認はRESTOREを記録し、社員マスタの有給残は表示用キャッシュとして同期する。

承認済み申請は本人が取消理由を入力して「取消申請中」にできる。元の承認者権限範囲にある別人が取消承認/取消却下を行う。承認済み打刻修正は直接巻き戻さず、新しい打刻修正申請で訂正する。

管理画面の社員一覧から「年休」を開き、GRANT / EXPIRE / ADJUSTを台帳へ登録できる。GRANTで10日以上の新規付与記録がある社員について、基準となる付与日から1年間の年5日取得状況を監視する。全日有給と午前/午後半休を取得実績へ算入し、会社規程上の法的区分が未確定の1/4日有給は年5日実績へ自動算入しない。

付与記録がない、または会社カレンダーが不足する場合は「判定材料不足」とし、法令対応済みとは表示しない。年5日未達で期限120日以内または期限超過の場合は通知する。

年休管理簿の保存期間や個別の付与方式・基準日統一/分割付与等は会社運用を確認し、システムの自動判定だけを専門家判断の代替にしない。

## 26. 実行環境とDB分離

実行環境は `DEVELOPMENT / STAGING / PRODUCTION` のいずれかとする。

- Script Property `FM_WORKS_ENVIRONMENT` 未設定時はSTAGING。
- DEVELOPMENT/STAGINGは既定DBへフォールバック可能。
- PRODUCTIONは `FM_WORKS_DB_ID` の明示設定を必須とする。
- PRODUCTIONでSTAGING既定DBを再利用することは禁止する。
- システム状態に現在の実行環境を表示する。
- 本番運用チェックはPRODUCTION以外を未完了として扱う。
- 試作PIN終了と実行環境昇格は別工程とし、誤って本番設定へ切り替わらないようにする。


## 27. 自動バックアップ時間トリガー

DBバックアップは管理者のログイン有無に依存させない。

- 毎日03時台にApps Script時間トリガーから実行する。
- 同じ日に既に成功していればスキップする。
- Script Lockで重複実行を防止する。
- 有効化時は時間トリガーを1件だけ作成する。
- 無効化時は対象トリガーを削除する。
- 管理画面からトリガーを再設定できる。
- 成功/失敗を監査ログへ記録する。
- 保持期間は90日。
- コピー後に全シートの存在・最終行・最終列を原本と照合し、整合性確認に成功したコピーだけを「成功バックアップ」と記録する。
- 整合性未確認の最新バックアップがある状態では本番READYにしない。


## 28. 労務計算モデル v0.9.6

所定外時間と法定区分を分離する。法定日次時間外は1日8時間超、法定週次時間外は日次時間外との二重計上を避けて週40時間超を算出する。深夜労働は22:00〜05:00、法定休日労働は会社カレンダーで明示した「法定休日」の実働とする。

`LABOR_RULE_PROFILE=UNCONFIGURED` の間は一般則ベースの参考値として表示し、本番READYと月次締めを禁止する。管理者が就業規則・36協定を確認し、GENERAL_JPと週開始曜日を保存して初めて設定済みとする。

月45時間超、月60時間超、法定時間外＋法定休日労働が単月100時間以上を注意表示する。36協定の起算月と特別条項の有無を設定し、年360時間、特別条項ありの場合の年720時間、45時間超が年6か月超、2〜6か月平均80時間超を監視する。

標準会社カレンダー生成は法定休日を自動推測しない。本番READYには今後90日内に「法定休日」の明示指定が必要であり、就業規則に合わせて管理者が設定する。変形労働時間制、フレックス、業種特例、会社固有の特別条項詳細は自動的に法令適合判定しない。

受入条件:
- 会社カレンダーで法定休日を明示できる。
- 月次で法定時間外・深夜・法定休日労働を確認できる。
- 月境界をまたぐ週も週40時間判定に前後日を含める。
- 未設定状態では本番READYと月次締めを拒否する。

## 32. 本番認証Fail-Closed v0.10.0

試作モードは明示設定がない場合に無効を既定値とする。

- STAGING / DEVELOPMENTでは、設定 `PROTOTYPE_MODE=TRUE` の場合に限り試作認証を許可する。
- PRODUCTIONでは、`PROTOTYPE_MODE` が誤ってTRUEのままでも共通PIN認証を強制的に無効化し、社員ごとのPIN認証だけを許可する。
- 公開認証設定APIは試作PINそのものを返さない。
- ログイン画面へ共通PINを表示しない。
- ログイン入力欄へ共通PINを自動入力しない。
- 本番運用チェックは、実効的に共通PINが無効でも設定値がTRUEならREADYにしない。

受入条件:
- TRUE + STAGING は試作モードを許可する。
- TRUE + PRODUCTION は試作モードを拒否する。
- FALSE + STAGING は試作モードを拒否する。
- Apps Script実行環境情報を取得できない単体テスト環境では試作ログインをFail-Closedする。
- CIが本番ガードとPIN非公開化を静的検査し、ロジックテストが環境境界を検証する。

## 35. 36協定の年次・複数月監視 v0.10.3

日本・一般則プロファイルを「設定済み」とするには、週開始曜日に加えて次を必須とする。

- 36協定の対象期間の起算月（1〜12月）
- 特別条項の有無（なし / あり。未確認は不可）

一般則の監視値は厚生労働省が示す基準を基礎とする。

- 時間外労働: 原則 月45時間・年360時間
- 特別条項がある場合の一般則上限: 年720時間
- 時間外＋法定休日: 単月100時間未満
- 時間外＋法定休日: 2〜6か月平均80時間以内
- 月45時間を超えられる月数: 年6か月まで

年次・複数月判定は、締め済み月の月次確定スナップショットと対象月の最新集計を組み合わせる。必要な過去月の確定データが不足する場合は「判定完了」とせず、不足警告を表示する。

これらは一般則の監視支援であり、変形労働時間制、フレックスタイム制、業種別特例、個別36協定の具体的上限を自動的に法令適合判定しない。

### 35.1 1/4日有給

現行の「1/4日有給」は会社規程上の根拠が未確定である。時間単位年休として扱う場合は労使協定・対象者・単位時間等の設定が必要であり、年5日の取得義務への算入を自動推定しない。

本番化前にProduct Ownerと労務担当が制度上の位置付けを確定し、Q-026を解消する。

## 36. 運用完全性・承認経路・CI強化 v0.10.4

### 36.1 承認経路

- MANAGERにも直属部下の承認待ち通知を表示する。
- 直属部下が残るMANAGER / ADMINをUSER・CALENDAR_EDITORへ降格、または退職扱いにする操作は拒否する。
- 直属承認者の設定が循環する場合は保存を拒否する。
- 直属承認者の選択肢は在籍中のMANAGER / ADMINに限定する。

### 36.2 本番READY

次を追加ブロッカーとする。

- 今後90日内に法定休日の明示指定が1日もない。
- 最新バックアップのコピー整合性が検証済みでない。

### 36.3 QA / Deploy

CIとDeployの両方でロジックテストとClient Contract Testを実行する。GitHub ActionsはNode 24対応のaction/runtimeを使用する。

### 36.4 アクセシビリティ

モーダルのアイコン型閉じるボタンには必ずアクセシブルネームを付ける。CIでラベルなしの共通閉じるボタンを禁止する。

### 36.5 Apps Script I/O

認証セル更新と複数セッション失効はセル単位の連続書込を避け、Range / RangeListでまとめて反映する。

## 37. レスポンス最優先化 v0.10.5

### 37.1 起動・ログイン

- 保存済みセッションがある場合、起動時は `resumeSession` 1回でセッション確認と初期表示データを返す。公開ログイン設定取得→セッション再開→初期データ取得の直列3往復を禁止する。
- 通常ログイン成功レスポンスにも初期表示データを同梱し、ログイン後に `getInitialData` を追加実行しない。
- 初期表示後に全メニューを自動先読みしない。未表示画面の通信はユーザー操作を邪魔しない。

### 37.2 画面遷移

- 工数・予定・申請は、ナビゲーションへのポインタ滞在またはキーボードフォーカスをユーザー意図として扱い、必要な場合だけ短い遅延後に先読みする。
- 既に表示済みデータがある画面は、そのデータを即表示したまま裏で再取得する。再取得のために既存画面をローディング表示へ戻さない。
- 通知など非必須通信は、初期表示後かつ他の通信がない時だけ実行する。

### 37.3 Apps Script / Sheets I/O

- ホーム集計から `getMonthlySummary` を呼ばない。ホームに必要な勤務時間・残業・打刻不備・工数差分だけを軽量計算する。
- 予定表は予定日列を日付範囲検索し、対象期間だけを取得する。
- 申請・年休・月次確認・月次確定履歴は社員IDで対象行を検索し、全件取得後の社員絞り込みを原則禁止する。
- 社員一覧、会社カレンダー年データ、プロジェクト、設定は `CacheService` で短時間キャッシュし、更新時に明示的に無効化する。
- 工数ページはプロジェクト一覧を同じレスポンスで遅延取得し、初期表示のためだけにプロジェクトマスタを読まない。

### 37.4 打刻

- 打刻前に読み込んだ当日タイムラインへ新しい打刻をメモリ上で追加してレスポンスを生成し、保存直後に同じ当日打刻を再読込しない。
- 打刻の成功応答を返すためだけの `SpreadsheetApp.flush()` を行わない。

### 37.5 性能回帰Gate

CIは、全画面の自動先読み復活、ホームからのフル月次集計、予定全件走査、ログインの追加初期データ往復、CacheService/社員ID索引読込の欠落、打刻後の再読込を性能回帰として検出する。

### 37.6 管理画面の遅延ロード

- 社員ページは社員管理データだけを取得する。
- 認証・サポートタブは社員認証情報、PIN再発行依頼、サポート設定だけを取得する。
- プロジェクトタブはプロジェクトマスタだけを取得する。
- 運用設定タブは認証・社員・プロジェクトの管理データを取得せず、保守情報だけを取得する。
- 管理データのクライアントキャッシュは `people / auth / projects` で分離し、異なるタブのキャッシュを誤流用しない。


## 38. ナビゲーション情報設計 v0.10.6

日常利用するトップ階層を、ユーザーの主要ジョブに合わせて次の5項目へ限定する。

- ホーム
- 勤怠
- 工数
- 予定表
- 申請

ADMINだけ区切り線の下へ「管理」を表示する。

既存機能は削除せず、次の親画面へ統合する。

- 月次 → 勤怠 > 月間
- 会社カレンダー → 予定表 > 会社カレンダー
- 社員 → 管理 > 社員・権限
- 設定 → 管理へ名称変更

旧URL/Hashの `#monthly`、`#companyCalendar`、`#people` は互換性のため保持し、親メニューをアクティブ表示する。

モバイル下部ナビゲーションは、ホーム / 勤怠 / 工数 / 予定表 / 申請の5項目とする。管理機能は管理ワークスペース内で扱う。
